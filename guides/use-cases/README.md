# 공통 활용 가이드

이 허브는 현재 상황에 맞는 시작점, 요청문, 결과물과 검토 경계를 찾는 안내입니다. 제품 스킬의 정확한 입력·완료 계약은 각 제품 가이드를 따릅니다.

## 무엇을 할 수 있나요

게임 기획 학습, 작은 설계 문제, 프로젝트 검토, 포트폴리오 증거 정리를 시작할 수 있습니다. 먼저 [사용자 경로](audience-paths.md)에서 현재 상황을 고르고, [결과물 카탈로그](output-catalog.md)로 보존할 파일과 사람 검토 지점을 확인하세요.

## 누구를 위한 가이드인가요

- `AUD-01` 게임 기획 입문 학생: 용어와 작은 관찰·설계 실습을 시작합니다.
- `AUD-02` 게임 기획 취업 준비생: 직무, 역기획, 포트폴리오와 면접 근거를 연결합니다.
- `AUD-03` 게임 기획 직무 전환자: 기존 경험을 전이 가능한 증거와 새 과제로 나눕니다.
- `AUD-04` 솔로·인디 게임 기획자: 제작 범위와 위험을 제한한 설계를 만듭니다.
- `AUD-05` 현업 게임 기획자: 한 시스템·콘텐츠·UX·경제 문제를 직접 다룹니다.
- `AUD-06` 팀 리드·교육자·멘토: 과제, 검토 기준, 피드백 흐름을 구성합니다.

## 역량·콘셉트·스킬 중 선택하기

문제의 공통 원리를 배우려면 역량 사례를, 장르·플랫폼·목표의 제약을 비교하려면 콘셉트 사례를, 입력과 산출이 분명한 한 작업을 처리하려면 전문 스킬을 선택합니다. 전체 범위가 아직 불명확하면 제품 오케스트레이터로 초안을 만든 뒤 필요한 전문 스킬로 좁힙니다.

## 탐색 순서

1. [사용자 경로](audience-paths.md)에서 현재 목표와 작은 첫 과제를 고릅니다.
2. [Studio 활용 사례](../game-design-studio/use-cases/README.md) 또는 [Career 활용 사례](../game-design-career/use-cases/README.md)에서 제품과 사례 관점을 선택합니다.
3. 제품별 [Studio 스킬 워크벤치](../game-design-studio/use-cases/skill-workbench.md) 또는 [Career 스킬 워크벤치](../game-design-career/use-cases/skill-workbench.md)로 입력과 직접 실행 결과를 확인합니다.
4. [결과물 카탈로그](output-catalog.md)에서 최소·선택·확장 결과와 handoff 경계를 확인합니다.
5. 막히면 [Studio FAQ](../game-design-studio/faq.md), [Career FAQ](../game-design-career/faq.md)와 이 문서의 [공통 FAQ](#공통-faq)에서 재개 경로를 찾습니다.

## 작업 규모 선택하기

입문은 개념 하나와 짧은 실습, 기초는 하나의 기획 문제 문서화, 응용은 여러 요소와 검토 기록 연결입니다. 포트폴리오는 공개 가능한 판단·검증 근거를 별도 Career Artifact로 정리하며, 전체 프로젝트는 제품 오케스트레이터와 사람 결정 지점을 포함합니다. 이 단계는 기간이나 품질을 보장하지 않습니다.

## 결과물 먼저 보기

모든 요청은 renderer와 이미지 provider가 없어도 남는 **최소 결과**부터 확인합니다. 이미지·도식·파생 형식은 **선택 결과**이며, 검토와 형식별 QA를 통과해 전달 또는 공개에 쓸 수 있는 자료는 **확장 결과**입니다. 파일 읽기 순서와 각 경계는 [결과물 카탈로그](output-catalog.md)에 있습니다.

## 공통 FAQ

### Q01. 어떤 플러그인부터 설치해야 하나요?

**결론:** 새 게임 설계는 Studio, 직무·포트폴리오 준비는 Career부터 선택합니다.\
**이유와 경계:** 두 제품은 Canonical Artifact가 다르므로 목적이 섞인다고 하나로 합치지 않습니다.\
**지금 실행할 요청문:** `내 목표를 Studio와 Career 중 어느 경로로 시작할지, 필요한 입력과 첫 결과로 비교해 줘.`\
**예상 결과물:** 시작 제품, 입력 목록, 최소 결과 목록입니다.\
**관련 가이드:** [사용자 경로](audience-paths.md), `guides/game-design-studio/README.md`, `guides/game-design-career/README.md`\
**권리·근거·승인:** 선택은 사람의 목적 판단이며, 채용·성과를 보장하지 않습니다.

### Q02. 자연어 요청과 직접 스킬 호출은 언제 구분하나요?

**결론:** 범위가 넓으면 자연어 요청, 작업이 한 가지면 직접 스킬 호출을 씁니다.\
**이유와 경계:** 직접 호출은 해당 스킬의 입력 계약을 따르며, 누락 입력을 사실처럼 채우지 않습니다.\
**지금 실행할 요청문:** `현재 입력으로 전체 흐름이 필요한지, 직접 호출할 스킬 하나가 충분한지 구분해 줘.`\
**예상 결과물:** 권장 진입점과 필요한 추가 입력입니다.\
**관련 가이드:** `guides/game-design-studio/skills/README.md`, `guides/game-design-career/skills/README.md`\
**권리·근거·승인:** 요청에 비공개 자료나 개인 정보를 넣지 말고, 선택 근거를 검토합니다.

### Q03. 아이디어 한 문장만 있어도 시작할 수 있나요?

**결론:** 가능합니다. 다만 한 문장은 가설이며 검증된 기획이 아닙니다.\
**이유와 경계:** 대상, 제약, 미정 사항을 분리해야 그럴듯한 사실을 만들지 않습니다.\
**지금 실행할 요청문:** `이 아이디어를 가정·질문·검증 기준으로 나눈 작은 기획 브리프로 바꿔 줘.`\
**예상 결과물:** 가정이 표시된 브리프와 다음 조사 항목입니다.\
**관련 가이드:** `ST-C01`, [AUD-01 경로](audience-paths.md#aud-01-게임-기획-입문-학생)\
**권리·근거·승인:** 제3자 작품·회사 자료를 원본처럼 붙이지 않고 출처와 사용 권한을 확인합니다.

### Q04. 전체 기획과 작은 특화 작업 중 무엇을 선택하나요?

**결론:** 지금 판단할 수 있는 가장 작은 문제부터 시작합니다.\
**이유와 경계:** 전체 문서는 의존성과 미해결 결정이 많을 때만 유용하며, 작은 문제를 자동으로 해결하지 않습니다.\
**지금 실행할 요청문:** `이 범위를 규칙 하나의 실습, 시스템 명세, 전체 프로젝트 중 어디까지로 제한할지 제안해 줘.`\
**예상 결과물:** 범위, 제외 항목, 검토 게이트입니다.\
**관련 가이드:** `ST-C03`, `ST-C08`, [결과물 카탈로그](output-catalog.md)\
**권리·근거·승인:** 범위와 우선순위는 담당자가 승인하며 일정·성과를 추정하지 않습니다.

### Q05. 기존 PDF·PPTX·DOCX·MD를 개선할 수 있나요?

**결론:** 검토 가능한 원본과 권한이 있으면 MD 중심으로 개선 계획을 만들 수 있습니다.\
**이유와 경계:** PDF·DOCX·PPTX의 실제 성공은 renderer와 형식별 검증에 달려 있습니다.\
**지금 실행할 요청문:** `권한이 확인된 이 문서의 사실·가정·미해결 결정을 분리하고 MD 개선안을 만들어 줘.`\
**예상 결과물:** 검토 메모, MD 초안, 재개 조건입니다.\
**관련 가이드:** `guides/game-design-studio/exports.md`, `guides/game-design-career/exports.md`\
**권리·근거·승인:** 소유권·공개 권한이 없는 문서와 개인정보를 입력하거나 배포하지 않습니다.

### Q06. Canonical Artifact는 왜 필요한가요?

**결론:** 재검토 가능한 원본과 판단 근거를 남기기 위해 필요합니다.\
**이유와 경계:** 이미지나 파생 문서는 원본을 대체하지 않으며, 한 제품의 Artifact를 다른 제품에 합치지 않습니다.\
**지금 실행할 요청문:** `이 작업의 Canonical Artifact에 남길 내용, 근거, 미해결 결정을 파일 구조로 정리해 줘.`\
**예상 결과물:** `content.md`, evidence, decisions 중심의 읽기 순서입니다.\
**관련 가이드:** [결과물 카탈로그](output-catalog.md)\
**권리·근거·승인:** 기록은 승인이나 사실 보장이 아니며, 근거의 공개 가능 여부를 별도 확인합니다.

### Q07. 이미지 prompt만 받거나 실제 생성을 어떻게 고르나요?

**결론:** 먼저 prompt와 사용 목적을 보존하고, 생성은 필요한 mode·capability가 있을 때만 요청합니다.\
**이유와 경계:** 생성 이미지는 처음부터 `concept-draft`이며 최종 리소스 또는 승인된 증거가 아닙니다.\
**지금 실행할 요청문:** `이미지 생성 없이 prompt package와 권리·검토 체크리스트만 만들어 줘.`\
**예상 결과물:** prompt, 사용 목적, 출처·승인 공백 기록입니다.\
**관련 가이드:** `guides/game-design-studio/image-assets.md`, `guides/game-design-career/image-assets.md`\
**권리·근거·승인:** 사람 검토와 권리 확인 전에는 공개·상용 사용을 주장하지 않습니다.

### Q08. Skillstead 도식과 표는 언제 구분하나요?

**결론:** 순서·분기·흐름은 도식, 비교·규칙·값은 표로 표현합니다.\
**이유와 경계:** 도식은 SVG source와 접근성 설명, lint·렌더·visual QA가 있어야 파생 PNG를 신뢰할 수 있습니다.\
**지금 실행할 요청문:** `이 정보를 표와 흐름 중 어느 형식으로 보여야 검토하기 좋은지, 근거와 초안을 제안해 줘.`\
**예상 결과물:** 선택한 형식, 접근성 설명, 검토 항목입니다.\
**관련 가이드:** `guides/game-design-studio/visualization.md`, `guides/game-design-career/visualization.md`\
**권리·근거·승인:** 도식의 렌더 성공은 내용 정확성이나 사람 승인이 아닙니다.

### Q09. PDF·DOCX·PPTX가 생성되지 않으면 무엇이 보존되나요?

**결론:** Canonical Artifact와 MD, export 준비 근거가 보존됩니다.\
**이유와 경계:** renderer capability가 없거나 QA가 실패한 형식은 성공으로 표시하지 않고 해당 형식만 재개합니다.\
**지금 실행할 요청문:** `renderer 부재를 전제로 MD와 export manifest를 보존하고, 형식별 재개 조건을 적어 줘.`\
**예상 결과물:** MD, capability 기록, 실패 형식의 resumable action입니다.\
**관련 가이드:** [결과물 카탈로그](output-catalog.md), `guides/game-design-studio/exports.md`\
**권리·근거·승인:** 실제 파일·format QA·visual QA evidence 없이는 배포 성공을 주장하지 않습니다.

### Q10. Studio 결과를 Career 포트폴리오로 어떻게 넘기나요?

**결론:** 공개 가능한 문제·판단·대안·검증 근거만 별도 Career Artifact에 입력합니다.\
**이유와 경계:** Studio와 Career의 Canonical Artifact는 결합하지 않으며, 팀 결과가 개인 기여를 증명하지 않습니다.\
**지금 실행할 요청문:** `이 Studio 작업에서 공개 가능한 문제·결정·검증 evidence만 추출해 Career 포트폴리오 브리프 입력으로 정리해 줘.`\
**예상 결과물:** 공개 가능성 확인 목록과 별도 portfolio brief 초안입니다.\
**관련 가이드:** [Studio → Career handoff](output-catalog.md#studio-career-handoff), `CA-C06`\
**권리·근거·승인:** NDA, 팀 PII, 권리 불명 자산, 검증되지 않은 팀 성과는 제외합니다.

### Q11. 학교·회사·팀 비공개 자료를 입력해도 되나요?

**결론:** 공개 권한과 기관 정책이 확인되지 않으면 입력하지 않습니다.\
**이유와 경계:** 익명화만으로 NDA·권리·개인정보 문제가 자동 해결되지는 않습니다.\
**지금 실행할 요청문:** `비공개 자료 없이 같은 기획 문제를 설명할 수 있는 중립적 가정과 공개 가능한 예시 구조를 만들어 줘.`\
**예상 결과물:** 비식별화된 문제 정의와 확인이 필요한 권한 목록입니다.\
**관련 가이드:** [결과물 카탈로그](output-catalog.md#studio-career-handoff)\
**권리·근거·승인:** 학교 AI 정책, 회사 보안 정책, 소유자 승인과 제3자 권리를 우선합니다.

### Q12. 플러그인 결과를 어디까지 믿고 어떻게 검증하나요?

**결론:** 초안과 체크리스트로 사용하고, 사실·가정·미해결 결정을 사람이 검토합니다.\
**이유와 경계:** 결과는 재미, 흥행, 채용, 법률 적합성이나 플랫폼 승인을 보장하지 않습니다.\
**지금 실행할 요청문:** `이 결과에서 검증된 사실, 가정, 누락, 모순, 사람 결정이 필요한 항목을 분리해 줘.`\
**예상 결과물:** 검토 큐, evidence gap, 다음 검증 요청입니다.\
**관련 가이드:** `ST-C08`, `CA-C07`, [사용자 경로](audience-paths.md)\
**권리·근거·승인:** 검토 기록은 근거 출처와 승인자를 대체하지 않으며, 공개 전 권리 확인이 필요합니다.
