# 프로젝트 기억은 이전 작업을 어떻게 이어 주나요?

프로젝트 기억은 검토가 끝난 게임 기획 교훈을 로컬에 보관하고 다음 작업에서 다시 확인하는 기능입니다. 일반적인 LLM Wiki의 장기 축적 원리를 가져왔지만, 근거와 사람 승인이 없는 내용을 지식처럼 합성하지 않도록 범위를 좁혔습니다.

## LLM Wiki 원리를 게임 기획에 적용한 방식

일반적인 LLM Wiki는 원문을 읽어 요약·개념·비교 페이지를 계속 갱신합니다. 프로젝트 기억은 자유롭게 합성하는 개인 위키가 아닙니다. 기준 기획 결과물과 근거를 원문으로 두고, 출처·적용 범위·만료·충돌을 검사한 교훈만 별도 기억으로 관리합니다.

AI가 작업 결과에서 찾은 교훈은 검토 대기 후보까지만 기록합니다. **이름이 확인된 사람이 승인해야 현재 기록이 됩니다.** 사람 승인 전에는 다음 작업에 적용하지 않습니다. 사용자가 문서 작업에 계속 적용하라고 명시한 선호도도 적용 범위를 확인한 뒤에만 승인 기록으로 남깁니다.

## 저장 계층과 원본

프로젝트 기억은 다음 세 계층을 나눠 관리합니다.

| 계층 | 역할 | 변경 규칙 |
| --- | --- | --- |
| **기준 기획 결과물과 근거** | `content.md`, `evidence.yml`, `decisions/`처럼 현재 작업의 판단 근거를 보관 | 기억이 내용을 대신하거나 자동 수정하지 않음 |
| **기억 원본** | `.game-design/memory/` 아래의 봉인된 추가 전용 Markdown 사건 기록과 사람 결정 | 기존 기록을 덮어쓰지 않고 새 사건을 추가 |
| **검색용 파생 자료** | 재생성 가능한 파생 색인, 목록, 사용 기록 | 손상되면 기억 원본에서 다시 생성 |

기억 원본은 플러그인 설치 폴더가 아니라 현재 작업 공간에 남습니다. 기본 `local` 모드에서는 Git 로컬 제외 목록에 `.game-design/`을 등록하며, 플러그인이 자동 커밋하거나 원격 전송하지 않습니다.

## .env 설정

작업 공간 루트의 `.env` 또는 실행 환경에서 다음 값을 설정합니다. 잘못된 값이 들어오면 공유 범위나 저장 한도를 넓히지 않고 안전한 기본값 또는 허용 범위 안으로 조정합니다.

| 변수 | 기본값 | 용도 |
| --- | --- | --- |
| `GAME_DESIGN_MEMORY_ENABLED` | **`true`** | `false`이면 기억 읽기·쓰기·후보·색인·사용 기록을 모두 끔 |
| `GAME_DESIGN_MEMORY_SCOPE` | **`project`** | `project`, `workspace`, `global` 중 검색 범위를 선택 |
| `GAME_DESIGN_MEMORY_MAX_ITEMS` | `5` | 한 작업에서 적용할 승인 기록 수를 1~10개로 제한 |
| `GAME_DESIGN_MEMORY_CANDIDATE_TTL_DAYS` | `30` | 승인 전 후보의 유효 기간을 1~365일로 설정 |
| `GAME_DESIGN_MEMORY_GIT_MODE` | **`local`** | `local`은 로컬 제외, `tracked`는 사용자가 직접 Git 추적 여부를 결정 |

한 번의 요청에서만 이전 기록을 제외하려면 “이번 작업에서는 이전 기억을 사용하지 마.”라고 적습니다. 이 요청에서는 기억 폴더를 읽거나 만들지 않고 기존 Studio·Career 작업만 진행합니다.

## 이전 기록을 다시 쓰는 순서

1. 플러그인이 기억 설정, 프로젝트 ID와 제품 영역을 확인합니다.
2. 현재 요청과 관련된 승인된 기록만 조회합니다.
3. 출처·범위·만료·충돌을 다시 검사하고 맞지 않는 기록은 이유와 함께 제외합니다.
4. 통과한 기억은 근거가 아니라 참고 자료로 Studio 또는 Career 작업에 전달합니다.
5. 작업이 끝나면 적용한 기억과 제외 이유를 사용 기록에 남깁니다.
6. 재사용할 가치가 있는 새 교훈은 검토 대기 후보로 제안합니다.
7. 이름이 확인된 사람이 후보를 승인·거부·폐기하면 새 결정 사건을 기억 원본에 추가합니다.

[![설정 확인부터 승인된 프로젝트 기억 재사용까지 이어지는 흐름](assets/shared/project-memory-reuse-flow.png)](assets/shared/project-memory-reuse-flow.svg)

위 정적 도식은 기억을 사용하지 않는 분기와 사람 결정까지 빠르게 보여 줍니다. [프로젝트 기억을 저장하고 다시 쓰는 Archify 흐름](assets/archify/suite/suite-project-memory-lifecycle.html)에서는 설정, 조회, 검증, 후보와 사람 승인 사이의 연결을 단계별로 살펴볼 수 있습니다.

## 기록하지 않거나 적용하지 않는 내용

**채팅 전체, 작업 폴더의 모든 문서와 사용자 행동을 자동 수집하지 않습니다.** API 키, 계정 정보, 개인 식별 정보, 회사 비공개 원문 전체와 근거 없는 성과 주장도 기록하지 않습니다.

이 기능은 Obsidian 저장소나 그래프 보기를 만들지 않으며 외부 LLM Wiki 서비스와 연동하지 않습니다. Markdown 기억을 자동으로 원격 동기화하지 않고, 기억 본문에 적힌 명령도 실행하지 않습니다. 출처가 달라졌거나 만료·충돌·손상된 기록은 승인 이력이 있어도 현재 작업에 적용하지 않습니다.

## 프로젝트 이동과 복구

프로젝트 기억까지 옮기려면 결과 폴더와 `.game-design/`을 함께 복사한 뒤 프로젝트 ID와 출처 파일을 확인합니다. 기억을 옮기지 않을 때는 결과 폴더만 복사합니다. 설치·업데이트·제거는 `.game-design/`을 만들거나 삭제하지 않습니다.

파생 색인이나 목록만 손상됐다면 “기억 상태를 점검하고 파생 색인을 다시 만들어 줘.”라고 요청합니다. 원본 사건이 손상됐거나 기록 갈래가 충돌하면 해당 기억을 격리하고 사람이 선택할 때까지 사용하지 않습니다. 복구가 끝나지 않아도 기억 없이 기존 기획 작업을 계속합니다.

제품별 적용 범위와 요청 예시는 [Studio 프로젝트 기억](game-design-studio/memory.md)과 [Career 프로젝트 기억](game-design-career/memory.md)에서 확인하세요.
