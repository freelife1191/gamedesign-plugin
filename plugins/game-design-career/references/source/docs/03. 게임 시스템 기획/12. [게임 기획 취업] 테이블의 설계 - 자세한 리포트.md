
게임 기획에서 **테이블을 설계하는 핵심 원칙**은 무엇인가요?테이블 설계는 단순히 데이터를 나열하는 것을 넘어, 데이터 관리의 편의성**, **사용 방법의 통일성**, **개발 효율성**, 그리고 **미래 확장성을 고려하여 기획자와 프로그래머 모두가 효율적으로 작업할 수 있도록 하는 것이 중요합니다.
## 1. 게임 기획에서 테이블을 설계하는 이유와 중요성
게임 기획에서 테이블을 설계하는 것은 단순히 데이터를 나열하는 것을 넘어, 데이터 관리의 편의성, 사용 방법의 통일성, 개발 효율성, 그리고 미래 확장성을 고려하여 기획자와 프로그래머 모두가 효율적으로 작업할 수 있도록 하는 것이 중요하다. 


### 1.1. 테이블 설계 전 고려해야 할 핵심 질문
![image]()
1. **테이블을 만드는 명확한 의도 파악**: 테이블을 설계하기 전에는 "이 테이블을 왜 만들어야 하는가?", "어떤 기획 데이터를 관리하기 위해 필요한가?"를 먼저 고민해야 한다. 
  1. 뚜렷한 의도 없이 포트폴리오 기획서에 테이블을 넣으면 멋있게 보일 것 같다는 이유만으로는 어설프고 이상한 테이블이 만들어질 수 있다. 
2. **테이블의 목적과 역할 정의**: 테이블이 어떤 데이터를 담고, 어떤 기능을 수행할지 구체적으로 정의해야 한다. 
  1. **장비 시스템 기획 예시**:
  1. **목적**: 장비 아이템을 대량으로 제작하기 위함이다. 
  2. **수행할 일**:
  - 장비의 기본 정보(이름, 설명, 카테고리, 등급, 리소스 등)를 정의한다. 
  - 장착 시 플레이어가 갖게 될 각종 효과와 속성, 스테이터스, 스킬 세트 등을 세팅하거나 연결한다. 
  - 제작한 장비를 장비 아이템 ID를 매개로 각종 콘텐츠의 보상, 랜덤 박스 구성품 등으로 세팅할 수 있어야 한다. 


### 1.2. 돌림판 이벤트 테이블 예시를 통한 이해
![image]()
1. **돌림판 이벤트의 테이블화 필요성**: 모바일 게임에서 흔히 볼 수 있는 돌림판 이벤트는 보상만 바꿔서 재사용하는 경우가 많기 때문에 테이블 형태로 만들어진다. 
2. **각 담당자의 역할**:
  1. **아티스트**: 이벤트 기획자가 기획한 UI 연출에 필요한 리소스를 그린다. 
  2. **프로그래머**: 이벤트 기획자가 기획한 규칙 작동 방식대로 돌림판 시스템을 구현하고, 설계한 테이블이 실제로 작동되게 만든다. 
  3. **기획자**:
  - 이벤트 규칙 작동 방식을 기획한다. 
  - 이벤트 UI 연출의 기획 의도를 정리한다. 
  - 돌림판을 돌릴 때 필요한 재화의 양, 보상과 확률, 누적 돌림 보상으로 요구할 누적 횟수와 보상 내용 등을 기획한다. 
  - 이러한 기획 데이터를 입력할 수 있는 테이블을 설계한다. 
3. **돌림판 이벤트 테이블의 구성 요소**: 실제 테이블은 더 복잡하지만, 간소화하면 다음과 같은 형태를 가진다. 
  1. **돌림판 보상 테이블**: 돌림판 위치, 보상 아이템과 수량, 당첨 확률을 제어한다. 
  - 이는 돌림판이 타이밍에 맞춰 바늘을 멈추는 방식이 아니라, 바늘 돌아가는 것은 연출일 뿐이고 결과는 확률에 따라 정해지는 방식일 때 필요하다. 
  2. **가격 및 재화 테이블**: 돌림판을 돌릴 때의 가격과 요구하는 재화 아이템이 무엇인지 제어한다. 
  3. **누적 보상 테이블**: 돌림판을 돌린 누적 횟수마다 보너스 보상을 주는 규칙이 있기 때문에, 몇 회차 누적일수, 어떤 보상, 그리고 그 보상의 수량을 제어한다. 


### 1.3. 기획 데이터의 구조화와 분류
![image]()
1. **데이터 구조화의 의미**: 테이블을 설계할 때 어떤 기획 데이터를 제작하고 관리할지 결정하는 일은 데이터 구조화를 의미한다. 
  1. 이는 게임에 필요한 데이터들의 공통적인 속성을 도출해 체계적으로 분류하고 관리하는 일이다. 
2. **캐릭터 속성 예시**:
  1. **인간의 고유한 아이덴티티 속성**: 이름, 외형, 생일, 국적, 출신지, 주민번호 등이다. 
  2. **게임 캐릭터의 속성**: 이름, 외형, 태생, 등급, 원소 속성, 기본 체력, 공격력, 방어력, 공격 속도, 치명확률, 치명피해, 효과 저항, 효과 적중, 1번 스킬, 2번 스킬, 3번 스킬, 리더 스킬 등이다. 
  3. 이러한 속성들이 바로 기획자가 만들어야 할 **기획 데이터**이다. 


### 1.4. 다양한 시스템별 기획 데이터 테이블 예시
![image]()
1. **캐릭터 성장 레벨 기획**:
  1. **기획해야 할 내용**: 경험치 누적 규칙, 레벨 상승 규칙, 경험치가 누적되지 않거나 레벨이 오르지 않는 예외 상황 처리 규칙, 레벨 업 시 등장하는 연출과 유저 인터페이스 등이다. 
  2. **관리해야 할 기획 데이터**: 각 레벨 숫자별로 요구되는 누적 경험치량이다. 
  3. **테이블 기획**: 레벨별 필요 누적 경험치를 작업할 수 있는 테이블을 기획한다. 
2. **캐릭터 랜덤 뽑기 기획**:
  1. **기획해야 할 내용**: 재화를 지불해서 랜덤한 캐릭터를 획득하는 규칙, 한 번에 열 개를 뽑으면 할인해 주는 규칙, 100번 뽑아도 오성이 안 나오면 다음에는 오성이 반드시 나오도록 하는 천장 시스템 규칙, 이벤트 기간 동안 특정 캐릭터만 등장 확률을 올려줄 수 있어야 한다는 규칙, 흥미진진한 뽑기 연출과 유저 인터페이스 등이다. 
  2. **관리해야 할 기획 데이터**: 랜덤 뽑기 상품의 이름, 가격, 나와야 할 캐릭터, 각 캐릭터들이 등장할 확률, 뽑기 이벤트 기간 중 어느 캐릭터를 확률 없이 뽑아줄 것인지 등이다. 
  3. **테이블 기획**: 랜덤 뽑기 관련 데이터들을 작업할 수 있는 테이블을 기획한다. 
3. **스킬 시스템 기획**:
  1. **관리해야 할 기획 데이터**:
  - **기본 정보**: 스킬 이름, 설명, 아이콘, 리소스명, 카테고리 등이다. 
  - **사용 조건**: 쿨타임, 마나 소모량 등이다. 
  - **효과 적용 방식**: 사정거리, 효과 적용 범위, 효과 적용 대상, 효과 적용 대상의 숫자, 타게팅 형태 등이다. 
  - **구체적인 효과**: 스킬 기본 효과와 추가 발동 조건, 추가 발동 효과 등이다. 
  - **연관 스탯**: 효과에 영향을 주는 연관된 스탯, 스탯 계수, 레벨당 상승치 등이다. 
4. **스토리 대사 기획**:
  1. **관리해야 할 기획 데이터**: 대사, 챕터, 대사 재생 순번, 대사 텍스트, 대사를 말하는 인물과 연결된 일러스트 배치 위치, 배경 이미지, 사운드 효과, 더빙, 대사마다 바뀌는 일러스트 표정과 효과 등이다. 
  2. **선택지가 있는 대사**: 선택지 묶음, 선택지 내용, 선택 결과로 연결되는 다음 대사 등도 기획 데이터로 입력해야 한다. 
5. **건물 시스템 기획**:
  1. **관리해야 할 기획 데이터**: 건물 이름, 건물 설명, 건물 카테고리, 건물 외형 리소스명, 가로/세로 길이, 환경 점수, 보너스 효과, 보너스 효과의 수치, 구입 가격, 건설 재료, 건설 재료 수량, 건설 시간, 건물에서 제공하는 레시피 목록 등이다. 


## 2. 효율적인 테이블 설계를 위한 구체적인 방법
테이블을 설계할 때는 단순히 데이터를 나열하는 것을 넘어, 기획자와 프로그래머 모두가 편하게 작업하고 구현할 수 있도록 효율적인 구조를 만드는 것이 중요하다. 


### 2.1. 출석부 이벤트 테이블 설계 실습
![image]()
1. **초기 테이블 구성**: 출석부의 이름, 시작 날짜, 종료 날짜, 이벤트 사진, 각 출석 횟수별 보상과 수량 등을 기획하고 작업하여 표로 나열한다. 
  1. **팁**: 예제 데이터를 몇 개 넣어보면서 빠진 것을 쉽게 찾을 수 있다. 
  2. **주의사항**: 출석부 1종당 표 한 줄을 사용해야 한다. 
  - 한 종류의 출석부를 여러 줄로 나누면 컴퓨터는 줄 단위로 데이터를 읽기 때문에, 이름만 같은 서로 다른 출석부로 인식하게 된다. 
  3. **문제점**: 이렇게 한 줄에 많은 양의 값을 쓰도록 기획하면 실제 작업하기에 여러모로 불편하고 비효율적이다. 
2. **테이블 분리 (쪼개기)**: 불편한 테이블을 두 개로 쪼개어 효율성을 높인다. 
  1. **분리된 테이블 예시**:
  - **출석부 성질 테이블**: 출석부의 이름, 시작일, 종료 날짜, 사진 파일 이름 등 출석부의 성질을 기획한다. 
  - **회차별 보상 테이블**: 회차별 보상과 수량을 기획한다. 
3. **테이블 간 관계 설정의 필요성**: 출석부 종류가 여러 개일 경우, 분리된 테이블 간의 관계를 설정하지 않으면 어떤 보상이 어떤 출석부에 속하는지 컴퓨터가 알 수 없다. 
  1. **예시**: 크리스마스 출석부의 보상(알, 알부화기, 몬스터볼 등)과 10년 출석부의 보상(골드, 열매, 기력의 조각 등)을 컴퓨터에게 알릴 방법이 없어진다. 
  2. 이는 하나의 출석부를 두 개의 테이블에 나눠 입력해서 생긴 문제이다. 


### 2.2. 테이블 간 관계를 연결하는 '키(Key)' 개념
![image]()
1. **키의 역할**: 테이블 데이터들을 연결해 주는 개념으로, 열쇠처럼 관련 있는 값들을 오픈시켜 준다. 
2. **키를 활용한 관계 설정 예시**:
  1. **출석부 키**: '로그인 이벤트 산타 피카라'라는 키를 가진 크리스마스 출석부 데이터가 있다고 가정한다. 
  2. **보상 테이블 연결**: 출석부 보상 테이블에서도 동일하게 '로그인 이벤트 산타 피카라' 키를 사용하는 값들이 해당 출석부의 보상으로 연결된다. 
  3. **다른 출석부 예시**: '로그인 이벤트 뉴 이어' 키를 가진 기념 출석부의 경우, 보상 테이블에서 같은 키를 사용하는 8번째 줄부터 13번째 줄까지의 값이 연결된다. 
  4. 이처럼 키를 통해 출석부 테이블과 출석부 보상 테이블의 관계가 완성된다. 
3. **다른 테이블과의 관계 연결**:
  1. **다국어 텍스트 데이터 (**스트링 테이블**)**: **스트링 키**라는 매개체를 사용해 출석부 테이블과의 관계를 이어준다. 
  2. **아이템 데이터 (아이템 테이블)**: **아이템 키**라는 매개체를 사용해 보상 테이블과의 관계를 이어준다. 
  3. **중요성**: 어떤 열쇠를 통해 어떤 테이블과의 관계를 형성해 줄 것인지를 기획해야 한다. 
  4. **직접 입력하지 않는 이유**: 출석부는 이미 만들어져 있는 아이템을 보상으로 주는 것이지, 아이템을 창조하는 역할을 하는 것이 아니기 때문에 아이템이나 스트링 데이터를 출석부 테이블에 직접 입력하지 않는다. 
4. **ER 다이어그램**: 테이블 간의 관계를 연결한 것을 도식화한 것을 **ER 다이어그램**이라고 부른다. 


### 2.3. 키의 종류: 기본 키와 외래 키
![image]()
1. 기본 키** (Primary Key)**:
  1. **정의**: 각 테이블의 값들을 고유하게 구분할 수 있게 해주는 대표 값으로, 주민등록번호와 같은 역할을 한다. 
  2. **예시**: 출석부 테이블의 '출석부 ID'는 출석부 테이블을 대표하는 기본 키이다. 
  3. **필수 조건**: 어떤 테이블이든 기본 키는 반드시 존재해야 한다. 
  - 당장 다른 테이블에서 외래 키로 당겨올 일이 없더라도, 프로그램 구조상 기본 키는 반드시 필요하므로 테이블 설계 시 어떤 컬럼을 기본 키로 사용할지 명시해야 한다. 
  4. **고유성**: 기본 키 역할을 하는 값은 반드시 고유해야 하며, 동일 테이블 안에서 중복이 있으면 안 된다. 
  - **예시**: 상점 물품 판매 테이블에서 상점 ID, 진열 순서, 아이템 ID, 아이템 수량, 가격 등은 고유하지 않을 수 있으므로, **상품 ID**와 같은 새로운 컬럼을 만들어 기본 키로 사용해야 한다. 
  - 서로 다른 테이블에서 겹치는 것은 상관없지만, 자신이 대표로 있는 테이블 안에서는 주민등록번호 역할을 해야 하므로 이미 사용한 기본 키 값과 동일한 이름의 기본 키를 같은 테이블 안에서 또 만들어서는 안 된다. 
2. **외래 키 (Foreign Key)**:
  1. **정의**: 다른 테이블의 기본 키, 즉 대표하는 값을 불러와서 연결 짓는 데 사용하는 것이다. 
  2. **예시**: 출석부 보상 테이블의 '출석부 ID'는 출석부 테이블의 '출석부 ID'를 당겨서 쓰고 있기 때문에 외래 키에 해당한다. 
  3. **고유성 활용**: 동명이인이 존재할 수 있는 이름 대신, 고유한 주민등록번호를 외래 키로 사용해야 정확한 데이터 연결이 가능하다. 
  - **예시**: 포켓몬 마을 명부의 사람 데이터를 참조해 세금을 관리하는 테이블이 있다면, 이름 대신 주민등록번호를 외래 키로 사용해야 어느 김 피카가 얼마를 내야 하는지 헷갈리지 않는다. 
  4. **주의사항**: 다른 테이블에서 값을 당겨올 때, 그 테이블에 없는 값을 쓰면 아무 일도 일어나지 않는다. 
  - **예시**: 아이템 테이블에 없는 아이템을 상점 물품 판매 테이블에 입력하면, 상점 진열 슬롯에 아무 아이템도 판매하지 않는 것처럼 보여진다. 
  - 현업에서도 이런 실수가 종종 발생하므로 유의해야 한다. 


### 2.4. 컬럼 이름 짓기와 시스템 규칙 정의
![image]()
1. **컬럼 이름 짓기**:
  1. **규칙**: 영어와 숫자, 언더바를 사용해서 만들며, 팀마다 정해진 규격을 따른다. 
  2. **신입 기획자**: 내부 규격을 알 수 없으므로 자신만의 일관적인 규칙대로 만들면 된다. 
  3. **표기법 예시**:
  - **카멜 표기법**: 알파벳 첫 글자는 소문자, 두 번째 단어부터는 첫 글자를 대문자로 표기한다. 
  - 파스칼 표기법: 모든 단어의 첫 글자를 대문자로 표기한다. 
  - 스네이크 표기법: 각 단어 사이에 언더바를 넣는다. 
2. **시스템 규칙 정리의 중요성**: 각 컬럼이 어떻게 활용되어야 하는지, 작성한 값이 어떤 식으로 게임에 반영되어야 하는지 등의 시스템 규칙을 정리해야 한다. 
  1. 신입 지망생들이 예시 테이블만 넣거나 테이블 관계도만 그리는 경우가 많지만, 사실 이 부분이 가장 중요하다. 
  2. 이 규칙을 작성하지 않을 거면 테이블 기획을 기획서에서 빼는 것이 낫다. 
3. **데이터 단위 명확화**: 숫자 데이터를 입력하는 컬럼의 경우, 그 단위를 명확히 해줘야 한다. 
  1. **시간**: 시간 단위, 분 단위, 초 단위 중 무엇으로 입력할 것인지 명시한다. 
  - **예시**: 스킬 쿨타임 컬럼을 만들 때는 이러한 규칙을 함께 명시해야 한다. 
  2. **거리/범위**: 픽셀 단위, 미터 단위, 게임 자체 단위 중 어느 단위로 값을 작성할 것인지 명시한다. 
  - **예시**: 공격 사거리나 스킬 적용 범위 컬럼을 만들 때 명시한다. 
  3. **비율**: 뽑기 등장 확률, 버프/디버프 효율, 데미지, 개수 같이 비율을 써야 하는 컬럼은 100, 100분율, 천분율, 만 분율 등 중에서 어느 단위를 쓸 것인지 정리해야 한다. 
  - 보통 소수점 단위보다는 만 분율이나 10만 분율을 사용하는 편이다. 
  4. **범위**: 최소값, 최대값처럼 범위 형식으로 입력해야 할 때는 이상/이하, 초과/미만 중 무엇을 쓸 것인지 명시해야 한다. 


### 2.5. 각 컬럼의 자료형 정의
![image]()
1. **자료형의 개념**: 컴퓨터가 테이블에 쓴 값을 문자로 읽어야 하는지 숫자로 읽어야 하는지 알지 못하기 때문에, 이 값이 어떤 종류의 값인지 친절하게 알려주는 것이 자료형이다. 
2. **대표적인 자료형**:
  1. **정수형**: 소수점이 없는 숫자이다. 
  2. **실수형**: 소수점을 쓰는 숫자이다. 
  3. **논리형**: 참과 거짓 두 가지를 나타낸다. 
  4. **문자형**: 문자를 쓴다. 
  5. 열거형: 미리 정해둔 목록에서 값을 선택하는 형태를 의미한다. 
  - 이 형태를 쓸 때는 꼭 목차도 함께 정해 줘야 한다. 
3. **자료형 정의의 완료**: 앞에서 배운 지식을 활용해 각 컬럼마다 어떤 자료형을 쓸 것인지 정의하면 테이블 설계가 완료된다. 
4. **자료형 일치 규칙**: 기본 키와 외래 키의 관계로 연결된 컬럼은 서로 동일한 자료형을 써야 한다. 
  1. **예시**: 출석부 테이블에 출석부 키를 문자형으로 정의했다면, 출석부 보상 테이블에서 사용하는 출석부 키도 문자형이어야 한다. 
  2. 어느 한쪽을 숫자형으로 쓰면 서로 똑같은 값을 입력하는 것이 불가능하다. 


### 2.6. 데이터 입력 규칙 및 아이디 발번 규칙
![image]()
1. 인자 값** 활용 규칙**: 테이블에 데이터를 입력할 때, 기획자가 사용할 규칙과 프로그램이 작동하는 규칙을 정의해야 할 때가 있다. 
  1. **목적**: 상황에 따라 변할 수 있는 것을 입력하고 싶을 때 사용한다. 
  2. **예시 (대사)**: 새로운 유저가 가입할 때마다 기획자가 유저에 맞는 맞춤형 대사를 테이블에 입력하는 대신, 특정 인자 값을 넣으면 특정 규칙에 따라 대체해서 출력해 달라고 프로그래머에게 요청한다. 
  - **구체적 예시**: "'플레이어 님'이시군요"라고 테이블에 입력할 테니, 플레이어가 입력한 닉네임으로 대체해서 출력해 달라고 요청한다. 
2. 스트링 테이블** 내 스타일 코드 규칙**: 스트링 테이블에서 내용 중간중간에 다른 폰트나 스타일을 넣어야 할 때 사용하는 코드도 있다. 
  1. **방법**: 코드 규칙을 만들어서 구현 요청하면 된다. 
  2. **구체적 예시**: "이 아이템을 구매하려면 **크리스탈 200개**를 지불해야 합니다. 계속하시겠습니까?"라는 팝업에서 '200개'를 굵은 글씨와 형광 핑크색으로 강조하고, '계속하시겠습니까' 전에 줄 바꿈을 하고 싶다면, 텍스트 중간중간에 코드를 넣는 규칙을 설계하고 구현 요청한 후 코드를 삽입한다. 
3. **아이디 발번 규칙**: 각 테이블에 기본 키가 되는 아이디의 발번 규칙을 지정하는 것이다. 
  1. **장점**:
  - 어떤 데이터인지 쉽고 빠르게 파악 가능하다. 
  - 데이터 실수를 줄일 수 있다. 
  - 데이터 변경 히스토리를 추적하기에 용이하다. 


## 3. 테이블 구조 설계 시 고려할 심화 지식
테이블을 만들 때는 "이 테이블을 왜 만들어야 하는가" 못지않게 "이 테이블을 왜 이런 구조로 만들어야 하는가"를 함께 생각하는 것이 중요하다. 


### 3.1. 장비 테이블 구조 설계 방안별 장단점
![image]()
1. **방안 1: 아이템 테이블에 장비 제작 **컬럼** 추가**:
  1. **구조**: 장비 테이블을 따로 만들지 않고, 기존 아이템 테이블에 장비 제작을 위한 컬럼을 추가하는 방식이다. 
  2. **장점**: 장비 이름, 설명, 등급, 리소스 연결 구조 등은 일반 아이템과 동일한 규칙으로 작동하기 때문에 효율적이다. 
  3. **단점**: 장비 제작 시 쓰이는 특수한 컬럼들을 대량으로 추가해야 하므로, 아이템 테이블의 컬럼이 지나치게 많고 복잡해질 수 있다. 
2. **방안 2: 장비 테이블을 따로 생성**:
  1. **구조**: 장비 테이블을 별도로 만들고, 그 안에서 장비의 기본 정보, 리소스, 장착 효과를 전부 세팅할 수 있게 만드는 방식이다. 
  2. **단점**: 장비도 일종의 아이템이기 때문에, 아이템 테이블과 장비 테이블을 따로 만들면 중복되는 컬럼이 많아 유지보수 비용이 높아질 우려가 있다. 
3. **방안 3: 효과만을 연결하는 별도 테이블 생성 (절충안)**:
  1. **구조**: 아이템 테이블에 작성한 장비 아이템 ID를 매개로 하여, 해당 장비의 전투 관련 효과를 세팅하는 용도의 신규 테이블에 연결하는 방식이다. 
  2. **장점**: 방안 1과 방안 2의 절충안으로, 아이템 테이블이 복잡해지는 것을 방지하면서 전투 관련 효과를 효율적으로 관리할 수 있다. 
  3. **단점**: 양 테이블 모두 데이터를 입력하고 관리해야 하므로 실수가 일어날 수 있다. 
4. **결론**: 어느 방식으로 테이블을 설계하든 장단점이 있으므로, 상황에 맞게 가장 효율적이고 합리적인 방법을 선택해야 한다. 


### 3.2. 테이블 설계 시 고려해야 할 네 가지 핵심 원칙
![image]()
1. 데이터 관리의 편의성: 기획자의 관리 편의성이 프로그래머의 구현 난이도보다 중시되어야 한다. 
  1. **이유**: 당장은 프로그래머가 구현하더라도, 앞으로 데이터를 지속적으로 생산하고 관리해야 하는 쪽은 기획자이기 때문이다. 
  2. **결과**: 잦은 휴먼 에러가 발생하면 프로젝트 전체에 큰 손해가 날 수 있다. 
2. 사용 방법의 통일성: 유사한 역할을 하는 컬럼은 되도록 비슷한 형태로 기획하는 것이 좋다. 
  1. **이유**: 유사한 역할을 하는 컬럼의 작동 방식이 서로 다르면 실수할 가능성이 높기 때문이다. 
3. 개발 효율성: 구현하려는 기능과 비슷한 시스템이 이미 테이블로 구현되어 있다면, 기존 테이블을 개선하는 방식으로 가는 것도 좋다. 
  1. **예시**: 퀘스트 시스템과 업적 시스템은 인터페이스만 다를 뿐 본질적인 작동 구조는 같으므로, 퀘스트 시스템이 이미 존재하는 상황에서 업적 시스템을 만들어야 할 경우 퀘스트 테이블에서 업적도 만들 수 있는 형태로 설계할 수 있다. 
  2. **주의사항**: 하나의 테이블이 너무 많은 역할을 겸한다면 관리 편의성이 저하되므로 적당한 수준을 찾아야 한다. 
4. 미래 확장성: 추후 확장될 거라고 예상 가능한 시스템들을 수용할 수 있는 방향으로 기획하는 것이 좋다. 
  1. **이유**: 확장성을 고려하지 않고 설계하면, 나중에 해당 시스템에 추가 기능을 붙이거나 개선할 때 제약이 너무 커서 무산되거나, 시스템 규모에 비해 쓸데없는 공수가 들어 개발 일정이 낭비될 수 있기 때문이다. 
  2. **습관**: 어떤 테이블을 만들든, 유사한 다른 시스템이 추후에 만들어질 여지가 있는지 체크하는 습관이 필요하다. 
  3. **예시**: 뽑기 시스템을 기획할 때, 지금 당장은 캐릭터 뽑기만 있지만 나중에는 장비 뽑기 또는 캐릭터와 장비가 모두 나오는 뽑기가 나올 수도 있을 것 같다면, 뽑기 구성품 테이블의 구성품 타입을 지정할 수 있는 컬럼을 만들어서 장비와 캐릭터를 모두 수용 가능한 형태로 만드는 것이 좋다.
