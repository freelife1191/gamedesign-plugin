
게임 기획에서 데이터 테이블의 핵심 역할은 무엇인가요? 데이터 테이블은 기획 데이터를 보기 좋게 정리하는 도구가 아니라, **기획 데이터를 게임에 반영하기 위한 핵심 도구**이며, 프로그래머가 구현한 엔진 기능을 통해 코드 형태로 변환되어 실제 게임에 구현됩니다.
## 1. 게임 기획에서 데이터 테이블의 이해와 중요성
게임 기획에서 데이터 테이블은 기획 데이터를 게임에 반영하기 위한 핵심 도구이며, 프로그래머가 구현한 엔진 기능을 통해 코드 형태로 변환되어 실제 게임에 구현된다.


### 1.1. **데이터 테이블**의 정의와 핵심 역할
![image]()
1. **데이터 테이블**은 게임의 기획 데이터를 넣기 위해 사용하는 표를 뜻하며, 일종의 툴과 같은 역할을 한다. 
  1. 게임의 다양한 요소들의 속성과 규칙을 정의하고, 이들 간의 상호 작용을 설계할 때 테이블을 사용한다. 
2. **데이터 테이블**의 핵심 역할은 기획 데이터를 보기 좋게 정리하는 것이 아니라, 기획한 데이터를 게임에 반영하기 위한 도구라는 점이다. 
  1. 취업 지망생들은 현업 테이블을 볼 기회가 없어 테이블이 기획 데이터를 보기 좋게 정리하는 역할이라고 오해하는 경우가 많다. 
  2. 기획자가 데이터 테이블에 작성한 값들은 프로그래머가 만든 엔진 기능을 통해 코드 형태로 변환되어 실제 게임에 구현된다. 
  3. 기획자는 편의상 엑셀 같은 스프레드시트 프로그램을 사용하지만, 실제로는 모든 값이 원시적인 형태로 변환되므로 엑셀의 셀 병합 기능은 변환된 파일에 반영되지 않는다. 
  4. 따라서 테이블을 설계하거나 사용할 때는 셀 병합 같은 기능을 사용하지 않아야 한다. 
3. '테이블'이라는 용어는 중세 시대 회계사들이 계산 편의를 위해 체크무늬 테이블에 동전을 올려놓으며 돈 관리를 했던 것에서 유래되었다. 


### 1.2. 기획 데이터 테이블과 플레이어 데이터베이스의 차이
![image]()
1. 많은 신입 지망생들이 **기획 데이터 테이블**과 **플레이어 데이터베이스**를 동일하게 보는 오해를 한다. 
2. **플레이어 데이터베이스**는 플레이어의 프로필, 계정 정보, 게임 내 통계, 아이템 보유량, 레벨 등 플레이어 정보를 서버나 클라이언트에 저장한 것을 뜻한다. 
  1. 플레이어가 발생시킨 플레이 데이터를 저장하지 않으면, 게임 접속 시마다 기존에 획득했던 아이템이나 경험치 정보가 모두 사라져 항상 빈털터리로 게임을 시작해야 한다. 
  2. 따라서 플레이어 정보를 클라이언트나 서버에 저장하는 것이 필수적이다. 
3. **플레이어 데이터베이스**에 저장되는 정보는 기획자가 직접 입력하는 기획 데이터가 아니다. 
  1. 플레이어가 레벨업을 하거나 아이템을 획득할 때마다 기획자가 회사에 가서 해당 플레이어의 최신 데이터를 테이블에 입력할 것이라고 생각하는 사람은 없을 것이다. 
  2. 하지만 많은 신입 지망생들이 **기획 데이터 테이블**을 설계하면서 플레이어 레벨, 닉네임 등 플레이어가 발생시킬 데이터를 테이블 항목으로 작성하는 경우가 많다. 
  3. 이는 플레이어가 행동할 때마다 기획자가 직접 플레이어 데이터를 입력하러 출근하겠다는 것과 마찬가지다. 
4. 플레이어가 발생시킬 데이터 구조의 설계는 기획자가 아닌 서버 프로그래머가 담당한다. 
  1. 기획자가 시스템 기획서에 작성해야 할 것은 시스템에 들어갈 콘텐츠, 즉 **기획 데이터**들을 어떻게 입력할 것인지에 대한 내용이다. 
  2. **플레이어가 발생시키는 데이터**의 예시는 플레이어 아이디, 가입 시점, 길드 이름, 포켓몬을 잡은 시점, 플레이어가 키우는 포켓몬, 현재 플레이어의 피카츄 레벨과 HP 등이다. 
  3. 반면, **기획자가 기획한 데이터**의 예시는 피카츄의 기본 HP, 레벨별 HP, 피카츄가 배울 수 있는 스킬 후보, 피카츄의 진화 단계, 피카츄가 진화하면 무엇이 되는가 등이다. 
  4. 레벨이나 스테이터스 같은 정보는 기획자가 기획한 데이터를 기반으로 플레이어가 플레이한 수준에 맞게 산출된다. 
5. 이 개념을 이해하기 어렵다면, 이상한 데이터 테이블을 시스템 기획서에 포함시켜 점수를 깎이는 것보다 테이블 관련 내용을 아예 빼버리는 것이 안전하다. 
  1. 신입에게 데이터 테이블 설계 능력까지 요구하는 경우는 드물며, 기획서에 테이블 설계를 넣는 것은 어디까지나 플러스 알파 정도의 요소이기 때문이다. 


### 1.3. **데이터 테이블**이 필요한 상황과 예외
![image]()
1. **데이터 테이블**이 필요한 주요 이유는 다음과 같다. 
  1. 동일한 구조의 기획 콘텐츠 데이터를 대량으로 생산 및 관리해야 할 때 필요하다. 
  1. 예를 들어, 몬스터를 많이 만들거나 퀘스트를 많이 만들 때 사용한다. 
  2. 라이브 서비스 중 기획 데이터의 잦은 추가, 수정, 삭제가 예상되는 경우에도 테이블을 설계한다. 
  1. 예를 들어, 출석 보상, 상점 판매 물품과 가격, 뽑기 구성품, 이벤트 미션과 보상 같은 것들이 해당된다. 
2. 테이블 설계가 필요한 구체적인 상황은 다음과 같다. 
  1. 테이블 작업이 필요한데 기존에 테이블이 없을 때 새로 설계한다. 
  2. 기존 테이블로 넣기 어려운 성질의 값이 있어서 기존 테이블을 개선해야 할 때도 설계한다. 
3. **데이터 테이블**이 없다면 다음과 같은 문제가 발생한다. 
  1. 모든 기획 데이터를 프로그래머가 하드 코딩하거나 기획자가 원시적인 형태로 직접 입력해야 한다. 
  2. 보상과 같이 운영 방향성이나 경제 밸런스를 고려하여 라이브 서비스 전까지 수정될 가능성이 높은 값들을 수정하기 위해 계속해서 프로그래머에게 수정을 요청해야 한다. 
  3. 하지만 자주 바뀔 수 있는 값들을 **데이터 테이블** 형태로 설계하고, 이 테이블의 값이 프로그램에 반영되도록 구현해 놓으면 기획자가 직접 값을 수시로 고칠 수 있어 편리하다. 
4. 모든 기획 데이터를 테이블 형태로 관리하는 것은 아니다. 
  1. 변경할 일이 거의 없는 기획 데이터는 **하드 코딩**하는 경우도 많다. 
  1. 예를 들어, 포켓몬스터 덱에 최대 여섯 마리까지 들어갈 수 있다는 점은 '6'이라는 숫자를 리밸런싱할 일이 거의 없으므로 테이블 설계를 하지 않는다. 
  2. 기획 데이터이지만 표 형태로 관리하기에 복잡하거나 불편한 경우도 있다. 
  1. 예를 들어, 몬스터가 배치될 맵의 X, Y, Z 좌표와 같은 경우이다. 
  2. 팀에 따라 이런 데이터도 테이블을 활용하기도 하지만, 보통은 엔진의 서브 레벨 파일에서 기획자가 직접 배치하는 형태를 취한다. 
  3. 던전 보스가 스킬을 쓰는 다양한 조건과 구체적인 상황 같은 경우, 보스 로직이 복잡하지 않은 게임이라면 테이블을 사용하기도 하지만, 보통은 비헤이비어 트리 같은 것을 사용한다. 
  4. 캐릭터 스킬, 모션, 이펙트, 사운드가 재생되는 타이밍 같은 섬세한 작업을 할 때에는 테이블과 **액션 전용 **툴을 병행해서 사용하는 경우가 많다. 
  5. 게임에 따라 개별 테이블로 만들기 애매한 값들을 모아 놓은 테이블을 따로 만들기도 하는데, 이를 게임 컨피그레이션이라고 부른다. 
  1. 이는 같은 구조를 가진 콘텐츠나 밸런스 값이 대량으로 필요한 경우가 아닐 때 사용한다. 


### 1.4. 데이터 테이블의 작동 방식과 기획자의 역할
![image]()
1. 테이블 기획은 테이블 제작의 시작일 뿐이다. 
  1. 테이블의 파싱(게임에 반영할 수 있는 원시적인 형태로 변환하는 것)과 게임 내 반영 로직을 프로그래머가 구현해 줘야만 그 테이블을 사용할 수 있게 된다. 
  2. 테이블을 기획하고 엑셀에 기획 데이터를 넣는 것만으로는 테이블이 작동하지 않는다. 
  3. 테이블은 마법의 주문이 아니기 때문이다. 
2. 기획한 테이블을 게임에 반영했을 때, 테이블에 작성한 데이터가 게임에서 어떤 식으로 동작해야 하는지를 프로그래머와 약속하는 과정이 필요하다. 
  1. 예를 들어, 아이템을 구매할 때는 상점 테이블의 가격 칼럼에 입력한 값만큼 재화를 지불하도록 요구해야 한다. 
3. 기획 지망생 대다수는 기획서의 테이블만 대충 구현해서 넣거나 예시 데이터만 채워 넣는 경우가 많은데, 이것은 테이블 기획이라고 할 수 없다. 
  1. 테이블의 역할, 관계, 테이블을 구성하는 각 컬럼들의 작동 방식을 문서로 설명해야 프로그래머가 테이블을 구현할 수 있다는 점을 잊지 말아야 한다. 
  2. 테이블 구현 과정이 필요한 만큼, 무턱대고 테이블을 기획하다 보면 개발력이 낭비되어 정작 더 중요한 것을 만들지 못할 수 있다. 
  3. 테이블을 확장성 있고 효율적으로 기획하지 못하면 더 많은 개발력을 낭비할 수 있다. 
  4. 따라서 테이블이 필요한 상황을 이해하고, 어떤 기획 데이터를 테이블로 만들 것인지에 대한 고민이 필요하다. 


## 2. **데이터 테이블**의 구성 요소와 실제 사례
데이터 테이블은 속성(칼럼)과 값들의 모음(행)으로 구성되며, 스트링 테이블, 다이얼로그 테이블, 상점 테이블, 캐릭터 테이블, 아이템 테이블 등 다양한 형태로 게임 기획에 활용된다.


### 2.1. 데이터 테이블의 기본 구성 요소
![image]()
1. **속성(칼럼)**은 표의 각 세로 줄들이 존재해야 하는 이유를 정의한 것이다. 
  1. 예를 들어, 1번 열에 쓰여진 값들은 상점 아이디, 2번 열에 쓰여진 값들은 정렬 순서 등이다. 
  2. 표의 세로줄, 즉 열 또는 칼럼이라고 부르며, 속성으로 정의되는 값들의 모음이라 생각하면 된다. 
2. **행(로우)**은 표의 가로줄을 뜻하며, 여러 속성으로 구성된 값들의 모음을 의미한다. 
  1. 예를 들어, 상점에서 네 번째 물품인 '사라'라는 상품을 구매하면 '만팔이' 아이템 1개를 주고, 재화 10만을 10만 개 내야 하며 할인율은 1%라는 것과 같은 정보가 하나의 행을 구성한다. 


### 2.2. 스트링 테이블의 역할과 활용
![image]()
1. **스트링 테이블**은 여러 문자열을 한 곳에 집중적으로 관리할 수 있는 테이블이다. 
  1. 기획 데이터뿐만 아니라 각종 UI, 알림, 팝업 등에 사용되는 문구들을 모아서 관리한다. 
2. **스트링 테이블**을 사용하면 다음과 같은 장점이 있다. 
  1. 게임 내에서 사용되는 모든 텍스트를 **스트링 테이블**에 저장하면 업데이트 또는 문구 변경 시 수정이 쉽다. 
  2. 여러 언어로 서비스되는 게임일 경우, 각 문자열을 키와 함께 저장하여 해당 키에 따라 각 언어에 대응하는 텍스트를 제공하도록 구현하기 쉽다. 
  3. 동일한 문자열이 여러 군데에서 중복 사용되는 경우, **스트링 테이블**을 사용하면 딱 한 번만 저장하고 키를 기준으로 저장소 위치를 가리키는 형태로 구현할 수 있어 메모리가 절약된다. 
3. **스트링 테이블**의 활용 사례로 '심즈' 게임의 '스턴' 번역 오류 사건이 있다. 
  1. '스턴'을 '기절'로 순화하는 과정에서 모든 '스턴'이라는 글자가 '기절'로 바뀌어 '보스턴 테리어'가 '보기전 테리어'가 되는 사건이 발생했다. 
  2. 이러한 현상은 한글화 과정에서 문자가 나오는 모든 장면을 포토샵으로 수정하는 방식이 아니라, 하나의 이름이나 문장을 한국어, 영어, 일본어 등으로 각각의 칼럼에 번역한 뒤, 이 값들의 대표가 되는 **'스트링 키'**를 게임에 넣어 쓰는 방식이기 때문에 발생했다. 
  3. 프로그래머는 문자열을 게임에 넣을 때 발급된 **스트링 키**만 사용하며, 플레이어 입장에서는 이 **스트링 키**가 자신이 설정한 언어 버전으로 바뀌어 보이게 된다. 
  4. '기절' 사태는 번역 담당자가 **스트링 테이블**에서 '컨트롤+모두 바꾸기' 기능을 사용했기 때문일 것으로 추정되며, 이는 해당 게임이 **스트링 테이블**을 사용하고 있다는 증거이다. 
4. **스트링 테이블**을 가장 많이 활용하는 테이블은 각종 스토리 대사들을 입력한 다이얼로그 테이블이다. 
  1. **스트링 테이블**에서 언어별로 문구를 입력하고 대표 **스트링 키**를 발급한 다음, 그 **스트링 키**를 **다이얼로그 테이블**에 가져와서 사용하는 방식이다. 
  2. 만약 **스트링 테이블**을 사용하지 않는다면, **다이얼로그 테이블** 안에 한국어, 영어, 일본어 버전을 모두 입력해야 했을 것이다. 
  3. 이렇게 구현해도 불가능한 것은 아니지만, 이 경우 대사를 말하는 캐릭터 이름을 입력하는 칼럼에 중복값이 불필요하게 많이 생겨 작업 비효율이 발생한다. 
  4. 대사는 한 줄 한 줄 달라도, 대사를 말하는 캐릭터는 동일한 경우가 대부분이기 때문이다. 
5. **다이얼로그 테이블**의 구조는 보통 대사가 시작되고 끝나는 지점을 기준으로 하나의 덩어리(챕터)로 묶은 다음, 챕터 이름을 동일하게 넣어 컴퓨터에게 같은 챕터임을 인식시키고, 같은 챕터 내에서의 재생 순서를 정하는 방식이다. 


### 2.3. **상점 **테이블의 역할과 구성
![image]()
1. **상점 테이블**은 아이템을 창조하는 것이 아니라, 이미 만들어진 아이템(즉, **아이템 테이블**에서 정의한 아이템)을 가져와서 상품으로 파는 역할을 한다. 
2. 따라서 상점에서 아이템의 아이콘 이름 등의 정보를 정의하는 것은 불필요하다. 
  1. 이미 만들어진 아이템의 주민등록번호 역할을 하는 **키**를 가져오면 된다. 
  2. 이러한 방식으로 설계하고 구현해야 한다. 
3. **상점 테이블**의 구조는 **아이템 테이블**에서 정의한 아이템의 **키**를 가져와 필요한 재화와 가격, 상점 카테고리 및 상점 내 진열 순서, 구매 가능 횟수 등을 정의하는 식으로 되어 있다. 


### 2.4. **캐릭터 테이블**의 역할과 구성
![image]()
1. **캐릭터 테이블**은 캐릭터를 창조할 때 사용한다. 
  1. 따라서 캐릭터를 창조할 때 어떤 기획 데이터가 필요한지 고민하면 쉽게 설계할 수 있다. 
2. **캐릭터 테이블**에는 다음과 같은 정보가 필요하다. 
  1. **캐릭터의 외형**: 아트 리소스가 필요한데, 아티스트가 그려준 여러 리소스 중 어떤 파일을 이 캐릭터를 창조하는 데 사용할 것인지 기획자가 결정한다. 
  2. 따라서 리소스 파일명을 넣는 칼럼이 테이블에 필요하다. 
  3. **캐릭터의 이름, 도감 설명, 등급, 카테고리, **속성**, 착용 무기 타입, 스킬셋 그룹** 등을 지정할 칼럼도 필요하다. 
3. 스킬의 경우, **캐릭터 테이블**에 모두 넣으면 테이블이 너무 복잡해지므로, 보통은 **스킬 테이블**을 따로 만들어 거기서 각종 리소스, 숫자, 알고리즘을 조합해 스킬을 창조한다. 
  1. 그 후, 스킬의 주민등록번호 역할을 하는 키** 값**을 **캐릭터 테이블**에 붙이는 방식을 많이 사용한다. 


### 2.5. **아이템 **테이블의 역할과 구성
![image]()
1. **아이템 테이블**은 아이템을 창조하는 데 사용된다. 
  1. **캐릭터 테이블**과 마찬가지로 아이콘, 스트링 리소스, 각종 숫자들을 조합해 아이템을 만들어낼 수 있다. 
2. 스트링 키를 발급하여 각 아이템에 고유한 키를 부여하면, **스트링 테이블**에서 **스트링 키**를 가져올 수 있게 된다. 
  1. 마찬가지로 **상점 테이블**, **출석 보상 테이블** 등에서 **아이템 테이블**의 **아이템 키**를 가져와 사용할 수 있게 된다. 
3. **등급** 같은 경우에는, 예를 들어 등급 칼럼에 '사'라는 값을 입력하면 아이템 상세 정보 UI에 별 네 개가 출력되고 아이콘 배경색이 보라색이 되도록 프로그래머와 함께 각 등급마다의 약속을 해야 한다. 
  1. 이 약속은 UI 아티스트와 하는 것이 아니며, UI 아티스트는 포토샵으로 별 한 개 아이콘을 그려줄 뿐이다. 
  2. 이 약속 또한 기획서에 명시되어야 한다. 
  3. 등급 칼럼에 999와 같이 약속되지 않은 값을 사용하면 아무 일도 일어나지 않거나 게임에 문제가 생길 수 있다. 
4. 리소스 명을 쓰는 칼럼을 설계할 때에도 파일명만 쓸 것인지, 확장자까지 쓸 것인지, 파일 경로까지 다 쓸 것인지 등은 프로그래머, 아티스트와 약속을 해서 정해야 한다. 
  1. 이 내용 역시 기획서에 명시되어 있어야 한다. 


## 3. **데이터 테이블**과 **유저 인터페이스(UI)** 기획의 연동
데이터 테이블은 유저 인터페이스 기획과 밀접하게 연결되어 있으며, 인터페이스 화면에 데이터 테이블의 값을 동적으로 표시하여 효율적인 UI 제작을 가능하게 한다.


### 3.1. 데이터 테이블과 **UI** 기획의 연동 방식
![image]()
1. **데이터 테이블**은 **유저 인터페이스(UI)** 기획과 연결된다. 
2. 인벤토리 같은 인터페이스를 만들 때 아이템 하나하나 글자만 다른 화면을 제작하는 것은 매우 비효율적이다. 
  1. 이러한 경우, 공통으로 사용할 하나의 인터페이스 화면만 만든다. 
  2. 데이터 테이블의 값이 들어갈 곳을 구멍처럼 뚫어 놓은 뒤, 플레이어가 선택한 아이템과 연관된 정보만 테이블에서 찾아서 그 구멍 뒤로 비춰지도록 구현한다. 
3. 아이템 상세 정보 화면을 예시로 들면 다음과 같다. 
  1. **아이템의 이름 칸**은 **아이템 테이블**에 있는 아이템 이름 스트링 키를 비추고 있다. 
  1. 정확히는 이 **스트링 **키는 **스트링 테이블**에 있는 **스트링 키**를 호출해 주는 **외래키** 역할을 하며, **스트링 키**에서 한 번 더 나아가 **스트링 테이블**에 현재 언어 설정에 해당하는 문구를 비추는 식이다. 
  2. **"캐릭터 육성 소재"**라는 문구는 어떤 아이템 정보를 보고 있느냐에 따라 달라지는 문구이므로, **아이템 테이블**에 있는 아이템 카테고리를 비추고 있을 것이다. 
  3. **아이템 등급 칸**에서는 **아이템 테이블**에 있는 아이템 등급이라는 칼럼 값을 비추고 있을 것이다. 
  4. 등급 칼럼의 값을 사용하면 별이 네 개가 찍히도록 구현되어 있을 것이다. 
4. 따라서 인터페이스를 기획할 때는 어느 부분에 구멍을 뚫을 것인지와 각 구멍에 어떤 테이블의 칼럼 값이 보이도록 할 것인지를 기획서에 작성해 줘야 한다. 


### 3.2. **데이터 테이블** 설계 능력 향상을 위한 퀴즈
![image]()
1. **캐릭터 **가차 상품을 만들 때 필요한 기획 데이터는 무엇일까? 
  1. 가차 상품은 캐릭터를 창조하는 것이 아니라, 이미 만들어둔 캐릭터들을 활용해서 제작한다는 사실을 잊지 말고 답변을 작성해야 한다.
