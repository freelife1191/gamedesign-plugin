# 에이전트·문체 품질·Sample 결과·UltraQA 설계

## 목표

게임 기획 플러그인이 자연어 요청을 실제 기획 작업으로 이어 가고, 결과 문서를 사람이 읽기 쉬운 게임 업계 문장으로 다듬으며, README의 예시마다 확인 가능한 Sample 결과를 제공하도록 보강한다. `docs/에이전트`의 역할은 현재 플러그인에 없는 책임만 선별한다. 마지막에는 README 요청 흐름, 역할 위임, 문체 보존, 이미지 설정, 승인 경계를 동적 UltraQA 시나리오로 검증한다.

## 검토한 접근

### 1. 후보 역할을 모두 이식

전투, 퍼즐, 성장, 경제, 시장, 테크니컬, 프로듀서, 비주얼 역할을 모두 추가하는 방식이다. 게임 장르별 질문은 늘지만 현재 역할과 경계가 겹치고, BUG 프로젝트의 팀 규모·플레이타임·Steam 전제가 범용 플러그인에 섞인다. 역할 수만 늘고 오케스트레이터가 어떤 역할을 골라야 하는지 불명확해져 기각한다.

### 2. 공백만 추가하고 중복 책임은 흡수

Studio에 `combat-encounter-reviewer`, `level-puzzle-reviewer`만 추가한다. 두 역할은 전투 가독성·대응 수단·지배적 조합과 퍼즐의 강제 해법·진행 불가·재시도 복구를 각각 검토한다. 크리에이티브, 성장, 경제, 테크니컬, 프로듀서, 비주얼 후보의 유용한 질문은 기존 역할에 최소 흡수한다. Studio와 Career에는 `game-design-writing-editor`를 공통 추가한다. 권장안이다.

### 3. 역할을 추가하지 않고 문서만 보강

기존 역할 문서에 모든 책임을 덧붙이는 방식이다. 역할 수는 유지되지만 전투·퍼즐 검토와 문체 검수가 기존 역할의 핵심 책임을 흐린다. 독립 테스트와 선택적 위임이 어려워 기각한다.

## 채택 범위

### 신규 역할

- Studio `combat-encounter-reviewer`: 입력, 발동, 적 반응, 보상, 전조, 대응 수단, 회복 구간, 지배적 조합, 보스 무력화를 증거 기반으로 검토한다.
- Studio `level-puzzle-reviewer`: 규칙, 필수·선택 경로, 피드백, 재시도, 초기화, 진행 불가, 비밀 경로와 접근성 대안을 검토한다.
- Studio/Career `game-design-writing-editor`: 사실, 추론, 제안, 수치, ID, 표, 링크, 승인 상태를 보존하면서 번역투, 근거 없는 과장, 영어 우선 표기, 기계적인 병렬 문장과 맥락 없는 코드 용어를 찾아 최소 수정한다.

세 역할 모두 검토 의견과 최소 수정안만 반환한다. 원본을 무단으로 덮어쓰거나 승인 상태를 바꾸지 않는다. 전투·퍼즐 역할에는 차단 권한을 주지 않는다. 문체 역할은 사실성 검증이나 업계 적합성 승인을 대신하지 않는다.

### 신규 스킬

Studio와 Career에 `polish-game-design-writing`을 추가한다. 이 스킬은 게임 기획 문서의 보호 대상과 승인 경계를 잠근 뒤, 함께 설치되는 `humanize-korean`을 문장 윤문 엔진으로 사용한다.

`humanize-korean`은 공식 [`epoko77-ai/im-not-ai`](https://github.com/epoko77-ai/im-not-ai)의 Codex 배포본을 두 플러그인에 번들한다. 2026-08-11 확인 기준 최신 릴리스는 `v2.3.0`, 태그 커밋은 `82137e858763dadb99561f194c5c00465735017b`, 라이선스는 MIT다. 심링크가 아닌 일반 파일로 `SKILL.md`와 전체 reference를 보존하고, 저장소·태그·커밋·릴리스 시각·파일 해시·라이선스를 vendor lock에 기록한다.

플러그인 설치 중 임의의 원격 코드를 실행하지 않는다. 대신 릴리스 준비 단계에서 공식 GitHub 최신 릴리스를 조회하는 검증·업데이트 명령을 제공하고, 검증된 최신 버전을 플러그인 패키지에 포함한다. 사용자는 Game Design Studio 또는 Career를 설치하면 `$humanize-korean`을 바로 사용할 수 있다. 네트워크를 사용할 수 없어도 번들 버전이 동작하며, 새 upstream 릴리스가 발견되면 검증·잠금 갱신 전까지 기존 버전을 안전하게 유지한다.

작업 순서는 다음과 같다.

1. 기획 문서와 증거·결정·승인 상태를 읽는다.
2. 변경 금지 대상을 잠근다: 사실, 수치, 날짜, 고유명사, 요구사항 ID, 표·링크·파일 경로, 사실/추론/제안 구분, 승인·보류 상태.
3. AI투·번역투·영어 우선·맥락 없는 코드 용어·근거 없는 과장을 진단한다.
4. 문단 구조와 문장 흐름을 최소 범위로 고친다.
5. 의미 보존 검사와 게임 기획 용어 검사를 통과한 초안과 변경 요약을 반환한다.
6. 사람 검토자가 수정본을 승인하거나 보류한다.

긴 문서는 절 단위로 처리하되 앞뒤 절의 용어, 결정, 전제를 다시 대조한다. 문체 수정으로 근거가 추가되거나 삭제되면 실패다.

`humanize-korean` 단독 호출은 일반 한국어 윤문에 사용한다. `polish-game-design-writing`은 그 앞뒤에 게임 기획 전용 보호·검증·승인 경계를 추가한다. 두 스킬을 하나로 합치지 않는다.

### 기존 역할 보강

- `lead-game-designer`: 주 방향과 현실적인 대안을 함께 비교하고, 기능 모음이 목표 경험을 흐리는지 확인한다.
- `system-economy-designer`: 초·중·후반 선택, 되돌리기, 반복 노가다, 재고 정리 피로, 무의미한 수치 장비를 점검한다.
- `production-feasibility-critic`: 가장 강한 반론, 작성 도구와 테스트 지점, 저복잡도 대안, 이전 계획을 점검한다.
- `art-brief-director`: 구도, 팔레트, 재질, 카메라, 움직임 기준과 제한된 대안 프롬프트를 점검한다.

시장·제품 전략가와 영상 공급자 전용 역할은 추가하지 않는다. 최신 시장 조사 스킬과 근거 등록부 없이 역할만 추가하면 가격·판매량·수요를 지어낼 위험이 있기 때문이다.

## 자연어 라우팅

- `보스전`, `전투`, `스킬 연계`, `적 패턴`, `encounter` 요청에는 전투·보스 검토자를 조건부로 선택한다.
- `퍼즐`, `레벨`, `비밀 경로`, `soft lock`, `초기화`, `재시도` 요청에는 레벨·퍼즐 검토자를 조건부로 선택한다.
- 문서를 작성하거나 고친 작업에는 구조 검토 뒤 문체 검수 스킬을 적용한다.
- 문체 검수는 도메인 검토를 대체하지 않는다. 전체 검토 역할은 기존 상한인 세 명을 넘지 않는다.
- 자동 라우팅은 자동 승인이 아니다. 선택한 스킬·역할·파일·보류 항목을 결과에 밝힌다.

## Sample 결과

README의 Studio 7개, Career 7개, 연계 4개 사례에 각각 Sample 결과 문서를 연결한다. Sample은 완성 답안이 아니라 결과 형태를 보여 주는 축약 예시다.

각 Sample은 다음을 포함한다.

- 원래 요청과 자동 선택된 작업 순서
- `content.md`에 들어갈 핵심 발췌
- 확인된 정보, 가정, 제안, 확인할 질문
- 예상 파일 목록과 읽는 순서
- 적용된 검토 역할과 남은 보류 항목
- 이미지가 필요한 경우 stable asset ID, 프롬프트, 생성 상태, 사람 검토 상태

허구 프로젝트·지원자 정보는 예시임을 표시한다. 취업 성공, 시장 성과, 재미, 일정, 법적 적합성, 이미지 권리를 보장하지 않는다.

## 이미지 생성 검토

현행 기본값 `IMAGE_GEN_MODE=prompt-only`, `IMAGE_MODEL=gpt-image-2`, `IMAGE_QUALITY=low`를 유지한다. 키가 있으면 OpenAI Images API만 사용하고 실패 후 Codex로 바꾸지 않는다. 키가 없고 호스트 이미지 기능이 확인되면 Codex 경로를 쓸 수 있다. 둘 다 없으면 프롬프트와 자리표시자만 남긴다.

`required`와 `all`은 문서 품질 프로필과 manifest에 선언된 이미지 슬롯만 처리한다. 문서에서 이미지를 무제한으로 추측하지 않는다. 생성물은 참고 시안이며, named human review 전에는 문서 승인이나 제작 후보로 승격하지 않는다. 실제 네트워크 호출은 기본 QA에서 실행하지 않는다.

현행 구현은 텍스트 프롬프트로 서로 독립된 이미지를 만드는 데까지만 지원한다. 마스터 이미지를 기준으로 캐릭터·배경·UI·아이템 파생 이미지를 만드는 기능은 별도로 추가한다. 공식 OpenAI Image API의 `gpt-image-2` 편집 엔드포인트(`/v1/images/edits`)와 복수 `image[]` 입력을 사용하고, 이 모델에서 허용되지 않는 `input_fidelity` 옵션은 보내지 않는다.

마스터 이미지 흐름은 다음 계약을 지킨다.

1. `asset_set_id`로 같은 이미지 묶음을 식별하고, 마스터와 파생 이미지에 서로 다른 stable asset ID를 준다.
2. 파생 이미지는 `derivative_of`, 참조 이미지 ID·파일 경로·SHA-256, 스타일·캐릭터 기준, 프롬프트 계보를 기록한다.
3. 자기 참조, 순환 참조, 작업 폴더 밖 경로, 심링크, 누락되거나 해시가 다른 참조 파일은 API 호출 전에 거부한다.
4. OpenAI 경로와 Codex 호스트 경로는 같은 참조 메타데이터를 받는다. 키가 있는 OpenAI 요청이 실패해도 다른 공급자로 자동 전환하지 않는다.
5. 생성 영수증에는 마스터·파생 관계, 참조 해시, 프롬프트 해시, 모델, 품질, 결과 해시를 남긴다.
6. 생성물은 사람 검토 전까지 참고 시안이다. 승인된 이미지만 문서나 내보내기 결과에 연결한다.

`.env.example`에는 실제 키를 넣지 않고 `OPENAI_API_KEY`, `IMAGE_GEN_MODE`, `IMAGE_MODEL=gpt-image-2`, `IMAGE_QUALITY`의 용도와 비용이 드는 명시적 실행 조건을 안내한다. 기본 테스트는 가짜 HTTP/호스트 어댑터와 작은 로컬 fixture만 사용한다.

## 함께 설치되는 도식화 스킬

두 플러그인은 기획 문서의 흐름도와 시스템 구조를 만들 수 있도록 다음 공식 스킬을 오프라인 번들로 함께 설치한다.

- Skillstead `svg-infographic` `0.9.0`: 일반 흐름도, 비교표, 검토·승인 흐름, 기획 한 장 요약을 editable SVG와 검증된 2배 PNG로 만든다. 공식 저장소는 [`kyungseo/skillstead`](https://github.com/kyungseo/skillstead), 고정 커밋은 `6e5b850f66716af9eb3c6a79f60e4f8ff5716dee`, 라이선스는 Apache-2.0이다.
- Archify `2.13.0`: 플러그인·기획 시스템의 architecture, workflow, sequence, data-flow, lifecycle을 검증된 standalone HTML로 만든다. 공식 저장소는 [`tt-a1i/archify`](https://github.com/tt-a1i/archify), 고정 커밋은 `2c1f8ac2ca28a26d0b68043ec80c9554e20ff0e3`, 라이선스는 MIT다.

Skillstead는 현재 포함된 `0.8.3`을 최신 안정판 `0.9.0`으로 갱신한다. Archify는 릴리스의 `archify.zip` SHA-256 `9aca2bc07812cbef2a7c177f4d3ef74669814c980621daea6e0fd9ee7ed8fd21`과 60개 일반 파일 closure를 검증한 뒤 번들한다. 두 스킬 모두 플러그인 설치 중 원격 코드를 실행하거나 최신 main을 따라가지 않는다. 릴리스 준비 명령에서만 공식 최신 안정판을 확인하고, 검증된 vendor lock·라이선스·정확한 파일 트리를 표준 빌드가 양쪽 제품의 `skills/` 아래로 복사한다.

오케스트레이터는 산출물에 도식이 필요하다고 판단하면 다음처럼 선택한다.

- 읽기 쉬운 정적 기획 흐름·비교·승인 경계는 `svg-infographic`을 사용한다.
- 여러 구성 요소, 소유권 경계, 데이터 이동, 상태 전환을 탐색해야 하면 `archify`를 사용한다.
- 둘 다 필요하면 Archify의 구조 원문과 Skillstead의 문서용 요약을 별도 산출물로 만든다. 하나의 결과가 다른 결과를 자동 승인하지 않는다.
- 생성된 SVG·PNG·HTML은 각 스킬의 validator와 시각 검수를 통과해야 하며, 사람이 읽기 어려운 글자·겹침·잘림·불필요한 영어 우선 표현이 있으면 실패로 처리한다.

## 문서 현행화

원본과 생성본을 구분한다. `products/*/plugin`, `shared`, `guides`, 루트 README를 원본으로 고치고 `plugins/*`는 표준 빌드로 재생성한다.

검수 기준은 다음과 같다.

- 한글 의미를 먼저 쓰고 영문 ID는 괄호나 코드로 보조한다.
- `혁신적`, `압도적`, `완벽한`, `자연스럽게 몰입` 같은 근거 없는 평가는 제거한다.
- `fact/inference/recommendation`은 처음에 한글 뜻을 함께 설명하고 계약 필드가 필요한 곳에서만 보존한다.
- 긴 문서는 목적, 입력, 작업, 결과, 검토·재개 순서가 읽히도록 구조를 정리한다.
- 현재 정책·시장·플랫폼 정보에는 출처, 검증일, 재검토일, 적용 범위와 한계를 둔다.
- 현업 기준은 목표 경험, 검증 질문, 상태·예외·복구, 접근성, 플레이테스트 근거, 운영·경제·UGC 안전, 본인 기여와 판단 근거를 포함한다.

모든 파일을 무조건 다시 쓰지 않는다. 검수 결과 문제가 있는 원본만 고치고, 검수 범위와 변경하지 않은 이유를 기록한다.

## UltraQA

UltraQA는 일반 경로와 다음 적대적 경로를 함께 검증한다.

- 자연어 요청이 skill ID 없이 올바른 전문 스킬·역할로 연결되는지
- 잘못된 JSON, 누락 필드, 매우 긴 문자열, 특수 Unicode, 경로 이동 문자열을 거부하거나 안전하게 보류하는지
- 사용자 문서 안의 프롬프트 인젝션이 지시로 실행되지 않는지
- 문체 수정 전후에 사실, 수치, ID, 표, 링크, 파일 경로, 승인 상태가 보존되는지
- 중단·재개·반복 요청이 기존 결과를 덮어쓰거나 자동 승인하지 않는지
- 오래된 상태, 더러운 작업 트리, 긴 실행, 비결정적 테스트, 성공 문구가 섞인 실패를 오판하지 않는지
- README 18개 예시가 실제 Sample 파일과 연결되고 해당 결과 검증기를 통과하는지
- 이미지 네 모드, API 키 우선, Codex 가능/불가, provider 실패, 사람 검토 경계가 유지되는지

동적 E2E가 실제 호스트 LLM·Codex 이미지 기능을 호출해야 하는 경우에는 네트워크를 쓰지 않는 격리 harness로 capability callback과 결과 계약을 검증한다. 실제 비용이 발생하는 이미지 호출은 opt-in smoke로 남긴다.

## 완료 기준

- 신규 역할·스킬의 실패 테스트와 정상·적대 시나리오가 통과한다.
- README 18개 사례가 Sample 결과와 연결된다.
- 이미지 기본값과 provider 경계가 테스트로 확인된다.
- 원본 문서 검수 보고서에 범위, 수정, 보존 이유가 기록된다.
- 표준 빌드, 문서 검증, 제품 E2E, 전체 테스트와 UltraQA 행렬이 통과한다.
- 임시 harness, 프로세스, 상태 파일이 정리되고 작업 트리가 깨끗하다.
