# 자연어 우선 요청과 README 윤문 설계

## 문서 정보

- **대상 독자:** Game Design Studio와 Game Design Career를 처음 설치한 사용자
- **목표:** 사용자가 플러그인 이름과 원하는 결과만 말해도 적절한 스킬과 검토 역할을 자동으로 선택하고, README가 이 기본 사용법을 먼저 설명하도록 한다.
- **범위:** 루트 `README.md`, 두 제품의 자연어 진입 계약, 라우팅·오케스트레이션 설명, 사례 묶음별 Skillstead 도식, 관련 회귀 테스트와 배포 스냅샷
- **범위 밖:** 146개 상세 요청문 카탈로그의 계약 변경, 기존 결과물 ID·파일 구조 변경, 사람 승인·권리·안전 경계 완화

## 확인한 현재 상태

Studio는 이미 `references/routing.json`을 기준으로 단일 분야 요청을 전문 스킬에 보내고, 복합·불명확 요청을 `orchestrate-game-design-project`로 보내도록 설계되어 있다. Career 오케스트레이터도 경력 단계와 목표를 진단한 뒤 필요한 최소 스킬 체인과 최대 세 개의 검토 역할을 선택한다.

문제는 루트 README다. 대표 사례 18개가 내부 사례 ID, 영어 계약 용어, 여러 개의 명시적 CLI 스킬 호출을 기본 사용법처럼 보여 준다. `채운 예시`라는 표제도 뜻을 바로 알기 어렵다. 이 구성은 실제 제품의 자연어 라우팅 능력을 숨기고, 사용자가 모든 스킬을 직접 골라야 한다는 인상을 준다.

## 검토한 접근법

### 접근법 1: 문구만 윤문

README의 어색한 표현만 고친다. 변경 범위는 작지만, 여러 스킬을 직접 호출하는 예시가 그대로 남아 사용 방식에 대한 오해를 해결하지 못한다.

### 접근법 2: 자연어 우선, 고급 제어는 접어서 제공

루트 README의 기본 예시를 App 자연어 한 줄 요청으로 바꾼다. 플러그인은 요청을 분석해 한 분야면 전문 스킬을, 복합·불명확하면 오케스트레이터를 사용한다. 사례 ID와 명시적 스킬 호출은 재현성, 재개, 특정 검토 단계가 필요한 고급 사용법으로 분리한다.

이 접근법을 채택한다. 현재 라우팅 계약을 살리면서 초보자의 진입 부담을 줄이고, 고급 사용자의 정밀 제어도 보존한다.

### 접근법 3: 명시적 스킬 호출 제거

README에서 모든 CLI 스킬 예시를 없앤다. 첫 사용은 편해지지만 자동 라우팅이 잘못되었을 때 경로를 고정하거나 중간 작업부터 재개하기 어렵다. 테스트와 운영에 필요한 재현성도 약해진다.

## 사용 모델

### 기본 사용

사용자는 플러그인을 선택하고 목표, 가진 자료, 원하는 결과만 말한다.

```text
@Game Design Studio 공개 가능한 플레이테스트 메모를 바탕으로
대상 플레이어와 핵심 재미가 드러나는 게임 기획 브리프를 만들어 줘.
확인되지 않은 내용은 미정으로 남겨 줘.
```

```text
@Game Design Career 시스템 기획 취업을 준비하고 있어.
현재 포트폴리오를 보고 부족한 역량과 12주 학습 계획을 정리해 줘.
확인할 수 없는 경력은 만들어 내지 마.
```

플러그인은 다음 순서로 처리한다.

1. 요청 목적과 원하는 결과를 파악한다.
2. 한 분야가 분명하면 해당 전문 스킬을 선택한다.
3. 여러 분야가 섞였거나 범위가 불명확하면 제품 오케스트레이터를 선택한다.
4. 결과에 영향을 주지 않는 빈칸은 `미정`으로 표시하고 진행한다.
5. 결과를 바꾸는 정보가 없을 때만 질문한다.
6. 서로 다른 검토 질문이 있을 때만 전문 역할을 최대 세 개 선택한다.
7. 사용한 스킬, 검토 역할, 결과 파일과 남은 결정을 마지막에 알려 준다.

### 고급 사용

다음 상황에서는 사례 ID나 명시적 스킬 호출을 사용한다.

- 같은 입력으로 같은 작업 경로를 재현해야 할 때
- 특정 전문 스킬만 실행해야 할 때
- 이미 만든 결과의 검토·도식화·내보내기 단계부터 재개할 때
- 테스트, 교육 또는 팀 표준 때문에 실행 순서를 고정해야 할 때

명시적 호출은 기본 사용법이 아니라 선택 가능한 제어 수단이다.

## README 정보 구조

### 첫 화면

`5분 안에 첫 결과 만들기`에서 App 자연어 요청을 먼저 보여 준다. 바로 아래에 “플러그인이 알아서 하는 일”을 짧은 목록으로 설명한다. CLI 예시는 별도 고급 사용 링크로 연결한다.

### 대표 사례 18개

각 카드의 표제와 필드를 다음처럼 바꾼다.

- `복사할 요청문` → `바로 써 보는 요청`
- `채운 예시 (App)` → `바로 복사해 쓰는 App 예시`
- `채운 예시 (CLI)` → `경로를 직접 지정하는 CLI 예시`
- `실행 흐름` → `플러그인이 선택하는 작업 순서`
- `예상 결과` → `받게 되는 결과`

App 예시는 사례 ID, 스킬 ID, `fact`, `inference`, `recommendation`을 요구하지 않는다. 필요한 경우 한국어로 `확인한 사실`, `해석`, `기획 제안`이라고 설명한다. 각 예시는 실제 사용자가 말할 법한 목표와 자료를 사용한다.

CLI 예시는 `<details>` 안의 고급 사용 영역으로 이동한다. 여러 스킬을 순서대로 입력해야 하는 것처럼 보이지 않도록, 권장 진입 스킬 하나와 필요한 경우의 후속 호출만 설명한다.

### 사례 묶음별 한 줄 요청

`Studio 기획 사례 7개`, `Career 학습·취업 사례 7개`, `Studio와 Career 연계 사례 4개`는 상세 카드를 열기 전에 한 줄 요청 표를 제공한다. 표는 목적, 바로 복사할 App 요청, 플러그인이 고르는 대표 경로, 받게 되는 결과를 보여 준다.

Studio 표에는 비전, 시스템, 플레이어 경험, 콘텐츠, 경제·라이브 운영, 제작 범위처럼 한 분야가 분명한 요청과 전체 프로젝트 요청을 함께 넣는다. Career 표에는 역할 탐색, 역기획, 포트폴리오, 면접, 성장 계획을 넣는다. 연계 표에는 Studio 결과의 포트폴리오 전환, 프로젝트 근거의 면접 연결, 기획서·이미지·발표 자료 준비, 실패한 파생 작업 재개를 넣는다.

각 상세 카드의 App 예시도 한 줄 자연어 요청으로 바꾼다. 사례 ID는 카드 제목과 고급 제어 영역에만 남긴다.

### Skillstead 자동 선택 도식

세 사례 묶음의 소개 바로 아래에 Skillstead SVG와 정확한 2배 PNG를 각각 하나씩 배치한다.

1. **Studio 자연어 요청 흐름:** 한 줄 요청 → 의도 분석 → 단일 전문 스킬 또는 프로젝트 오케스트레이터 → 필요한 검토 역할 → 기준 결과 폴더 → 사람 검토
2. **Career 자연어 요청 흐름:** 한 줄 요청 → 경력 단계·목표 진단 → 최소 스킬 체인 → 근거 중심 검토 역할 → 학습·취업 결과 → 멘토 또는 본인 검토
3. **Studio·Career 연계 흐름:** 한 줄 요청 → Studio 원본·공개 범위 확인 → Career 전환 스킬 → 결과 검토 → 포트폴리오·면접·발표 자료 → 사람 승인 또는 보류

도식에는 대표 스킬 이름을 한국어로 먼저 쓰고 영문 ID를 보조 표기한다. 모든 경로가 매번 같은 스킬을 실행한다는 뜻으로 보이지 않도록 `요청에 따라 선택`과 `필요한 경로만 실행`을 명시한다. 자동 선택과 자동 승인을 구분하고, 마지막에는 이름 있는 사람의 승인·보류 게이트를 둔다.

### 결과 설명

내부 결과 ID보다 한국어 결과 이름을 먼저 쓴다. `Canonical Artifact`는 첫 등장에만 `기준 기획 결과 폴더 (Canonical Artifact)`로 설명하고 이후에는 `기준 결과 폴더`로 쓴다. `blocker receipt`는 `중단 사유 기록`, `handoff`는 `다음 작업 인계`로 쓴다.

## 실제 제품 계약 보강

두 제품은 다음 규칙을 명시적으로 보존한다.

- App 자연어 요청은 사용자가 개별 스킬 이름을 몰라도 처리한다.
- 직접 일치하는 한 분야 요청은 해당 전문 스킬로 보낸다.
- 복합·불명확 요청은 제품 오케스트레이터가 최소 스킬 체인을 고른다.
- 사용자가 스킬을 명시하면 그 선택을 우선하되 안전·권리·사람 승인 경계는 유지한다.
- 선택한 스킬과 검토 역할을 결과 보고에 공개한다.
- 자동 선택은 자동 승인을 뜻하지 않는다.

이 규칙을 제품 원천의 오케스트레이터 문서, 패키지 README와 플러그인 기본 요청 예시에 반영한다. 생성된 `plugins/` 스냅샷은 표준 빌드로만 갱신한다.

## 윤문 규칙

루트 README는 114 KB이므로 `humanize-korean`의 5,000자 제한에 맞춰 섹션 단위로 나눠 윤문한다.

- 링크 대상, 파일 경로, 명령, 사례 ID, 스킬 ID와 수치는 바꾸지 않는다.
- 안전·권리·사람 승인 문장의 의미를 줄이지 않는다.
- 한국어 설명을 먼저 쓰고 영문 식별자는 괄호나 코드 표기로 보조한다.
- AI 특유의 반복 도입, 같은 문장 구조, 번역투와 불필요한 영어 병기를 줄인다.
- 세 항목 이상은 목록이나 표로 정리한다.
- 문단은 한 가지 행동이나 개념만 설명한다.
- 각 섹션 윤문 후 링크·ID·명령의 보존 여부를 검사한다.

## 테스트 설계

구현은 테스트 주도로 진행한다.

1. 루트 README 계약에 자연어 우선 소개, Studio·Career 한 줄 요청, 자동 선택 설명을 요구한다.
2. 대표 사례 18개에서 `채운 예시`, 기본 App 요청의 사례 ID, 기본 App 요청의 명시적 스킬 체인을 거부한다.
3. 세 사례 묶음이 목적별 한 줄 요청 표와 대표 자동 선택 경로를 제공하는지 확인한다.
4. 각 사례가 한국어 결과 이름과 사람 검토 경계를 유지하는지 확인한다.
5. Studio와 Career 제품 계약에 단일 분야 직접 라우팅, 복합·불명확 오케스트레이터 라우팅, 명시적 선택 우선, 선택 결과 보고를 고정한다.
6. Skillstead 도식 세 개의 정확한 노드·엣지, 대표 스킬, 선택 경로, 사람 승인 게이트와 점선 재개 경로를 계약으로 고정한다.
7. SVG lint, 정확한 2배 PNG, 글자 잘림·찌그러짐·흐림·겹침·중간 토큰 분할 검사를 실행한다.
8. 기존 링크, 18개 사례 ID, 30개 설치 스킬, 18개 역할, 결과 파일 구조와 Archify·Skillstead 링크가 그대로인지 확인한다.
9. 표준 빌드 검사, 가이드 검사, 제품 검사와 전체 테스트를 실행한다.
