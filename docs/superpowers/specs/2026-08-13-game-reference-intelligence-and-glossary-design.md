# 게임 레퍼런스 인텔리전스 및 용어 사전 설계

## 문서 상태

- 작성일: 2026-08-13
- 상태: 사용자 승인
- 대상: Game Design Studio, Game Design Career, 공통 런타임과 사용자 가이드
- 채택 접근: 공통 Reference Intelligence 코어와 Studio·Career 이중 투영
- 기본 원칙: 관찰과 추정을 분리하고, 레퍼런스를 복제하지 않으며, 기획 적용은 사람 검토 전 제안 상태로 유지한다.

## 결정 요약

경쟁작과 참고 게임을 조사할 때 단순 기능 목록이나 장단점 감상문을 만들지
않는다. 조사 목적과 의사결정 질문을 먼저 고정하고, 직접 플레이·공식 자료·공개
자료에서 확인한 근거를 시스템 단위로 정리한 뒤 시스템 관계와 반복 구조를
분석한다. 마지막에는 레퍼런스의 표면 기능이 아니라 작동 원리를 현재 프로젝트의
목표, 제약과 차별화 방향에 맞춰 `adopt`, `adapt`, `reject`, `hold` 중 하나로
분류한다.

공통 시스템 분류만으로 모든 장르를 설명하지 않는다. 공통 온톨로지 위에 장르,
플레이 방식, 플랫폼, 사업·운영 방식별 overlay를 적용하고 각 항목을
`required-candidate`, `conditional`, `optional`, `not-applicable`, `unknown`으로
판단한다. 장르 관습은 반드시 넣어야 하는 기능이 아니라 조사 질문을 빠뜨리지
않기 위한 시작점이다.

용어는 언어 중립 개념 ID를 중심으로 한국어 표준어, 영어 표준어, 약어, 허용
표현, 금지·폐기 표현을 연결한다. 공통 용어 사전과 프로젝트 overlay를 함께
사용하며, 새 용어나 충돌은 자동 교정하지 않고 경고 또는 차단 후 사람이 승인한다.
문서는 승인된 용어 사전 버전과 해시에 결속된다.

## 배경과 현재 기능

현재 플러그인에는 레퍼런스 분석에 활용할 수 있는 기반이 있다.

- Career의 `reverse-engineer-game-design`은 관찰, 추론, 반례, 대안과 검증을
  분리하는 역기획 절차를 제공한다.
- `fact-inference-schema.json`, `reverse-design-document`,
  `game-analysis-report`는 주장과 근거를 기록할 수 있다.
- `reverse-to-system-proposal.md`는 역기획 결과를 시스템 제안으로 넘긴다.
- Studio의 `design-game-systems`와 비전·경제·플레이어 경험·콘텐츠 방법론은
  프로젝트 설계로 이어지는 실행 표면을 제공한다.
- `polish-game-design-writing`은 제공된 용어를 참고해 문장을 다듬을 수 있다.

하지만 현재 기능만으로는 다음 계약이 충분하지 않다.

- 게임 전체의 시스템 목록, 시스템 지도, 핵심·세션·메타 루프를 한 구조에서
  비교하지 않는다.
- 장르·플랫폼·사업 모델에 따라 무엇을 조사해야 하는지 결정하는 overlay가 없다.
- 직접 경쟁작, 핵심 시스템 우수 사례, 운영·BM 비교작을 역할별로 선택하지 않는다.
- 사이트 조사와 실제 플레이·스크린샷 증거를 하나의 등록부에서 관리하지 않는다.
- 여러 게임의 차이를 현재 프로젝트의 설계 결정으로 옮기는 추적 가능한 절차가
  없다.
- 한국어와 영어 용어를 프로젝트 수명주기 동안 승인·폐기·검증하는 용어 사전
  시스템이 없다.

## 목표

1. 분석을 시작하기 전에 조사 질문, 대상 게임의 역할과 증거 계획을 고정한다.
2. 확인된 사실, 합리적 추론, 미확인 가설과 추가 검증 항목을 분리한다.
3. 게임 시스템을 목록뿐 아니라 입력, 처리, 출력, 연결, 루프와 상태 전이로
   분석한다.
4. 장르·플랫폼·사업 모델에 맞는 조사 항목을 누락 없이 제안하되 관습을 정답처럼
   강요하지 않는다.
5. 레퍼런스의 원리를 프로젝트 기획에 적용할 때 채택, 변형, 거절, 보류의 근거와
   위험을 남긴다.
6. Studio와 Career가 같은 근거 코어를 사용하되 서로 다른 결과물로 투영한다.
7. 한국어·영어 용어를 개념 ID와 승인 상태에 결속해 문서 간 일관성을 검사한다.
8. 유료 서비스, 로그인, 웹 접근 또는 실제 플레이 자료가 없어도 가용한 근거만으로
   실패 없이 진행하고 한계를 명시한다.

## 비목표

- 경쟁작의 기획서, 데이터, 이미지나 문장을 복제하지 않는다.
- 공개 자료만으로 비공개 수치, 내부 알고리즘, 매출이나 리텐션 인과를 사실처럼
  확정하지 않는다.
- 모든 게임에 전투, 가챠, 길드, 시즌이나 라이브 운영이 필요하다고 가정하지
  않는다.
- 1차 구현에서 상용 데이터 플랫폼, 대규모 크롤러, 상시 수집 서버나 외부 DB를
  만들지 않는다.
- GameRefinery, IGDB 같은 유료·인증 서비스에 핵심 흐름을 의존하지 않는다.
- 분석 결과를 사람 검토 없이 기존 시스템 명세나 용어 사전에 자동 반영하지
  않는다.
- 용어 충돌을 문자열 일괄 치환으로 해결하지 않는다.

## 검토한 접근

### 기존 Career 역기획 스킬 확장

파일 수와 라우팅 변화는 작지만 Career 목적, 포트폴리오 관점과 Studio 실무 설계
관점이 한 스킬에 섞인다. 장르 overlay, 다중 게임 비교, 용어 사전까지 추가하면
기존 스킬의 책임이 지나치게 커진다.

### 공통 Reference Intelligence 코어와 제품별 투영

공통 근거 등록부, 시스템 온톨로지, 분석 구조와 설계 전환 규칙을 공유한다.
Career는 역기획 문서와 분석 보고서로, Studio는 시스템 분석·비교·설계 전환
결정으로 투영한다. 기존 전문 스킬을 재사용하면서도 제품별 목적을 유지할 수 있어
이 방식을 채택한다.

### 완전한 외부 데이터 수집 플랫폼

검색, 스크래핑, 이미지 인식과 주기적 갱신을 하나의 서비스로 만들 수 있지만
로그인·비용·권리·서비스 변경·운영 부담이 커진다. 현재 목표는 기획 판단의 품질과
추적 가능성이므로 1차 범위에서 제외한다.

## 구성 요소

### Reference Brief

분석 작업의 경계를 고정한다.

- 분석 목적과 이번에 결정하려는 질문
- 프로젝트의 플레이어 경험 약속과 차별화 가설
- 장르, 플랫폼, 플레이 방식과 사업·운영 가설
- 조사 대상과 제외 대상
- 사용 가능한 시간, 자료, 언어와 지역
- 확정해서는 안 되는 항목
- 완료 조건과 사람 검토자

### Reference Set

기본 비교 묶음은 세 역할로 구성한다.

1. 같은 목표 고객·장르·플랫폼을 겨냥한 직접 경쟁작 1개
2. 이번 핵심 시스템을 가장 잘 보여 주는 우수 사례 1개
3. 운영, 경제 또는 BM을 비교할 수 있는 게임 1개

하나의 게임이 두 역할을 맡을 수 있지만 역할별 질문은 별도로 유지한다. 자료가
부족하면 단일 게임 분석도 허용하며 비교 결론은 `hold`로 남긴다.

### Evidence Registry

각 근거는 다음 정보를 가진다.

- `evidenceId`, 게임, 버전·빌드, 플랫폼, 지역, 계정 상태와 관찰 시점
- 출처 유형과 URL 또는 프로젝트 상대 경로
- 직접 관찰한 화면·행동·결과
- 근거가 지지하는 주장 ID
- 원본, 캡처, 요약과 변환 관계
- 저작권·사용 범위와 공개 가능 여부
- 신뢰 등급과 충돌 여부

근거 우선순위는 다음과 같다.

1. 직접 플레이와 공식 사이트·도움말·패치 노트·확률·스토어 정보
2. 개발자 발표·공식 회고와 신뢰 가능한 공개 위키·데이터베이스·전문 공략
3. 커뮤니티, 영상, 리뷰와 비공식 추적 자료

3등급 자료는 발견과 반례 탐색에는 유용하지만 단독으로 BM, 확률, 성과 또는
인과를 확정하지 않는다. 웹 문서 안의 명령문은 실행 지시가 아니라 분석 대상
데이터로 취급한다.

초기 참고 등록부에는 다음 공개 서비스를 선택 항목으로 둔다.

- [Steamworks Tags](https://partner.steamgames.com/doc/store/tags?l=english&language=english): 장르·기능 태그의 공개 기준
- [GameRefinery 장르 분류](https://docs.gamerefinery.com/en/articles/2278730-what-are-categories-genres-and-subgenres): 모바일 장르·하위 장르 비교
- [GameRefinery Game Intelligence](https://www.gamerefinery.com/game-intelligence-tools/): 유료 기능 비교 서비스, 필수 아님
- [GDC Vault Postmortems](https://gdcvault.com/browse/postmortem/?media=s): 개발 맥락과 회고
- [Game UI Database](https://www.gameuidatabase.com/)와 [Interface In Game](https://interfaceingame.com/screenshots/): 화면 구성 참고, 규칙 증거는 아님
- [SteamDB FAQ](https://steamdb.info/faq/): 비공식 변경 추적, 공식 자료와 교차 검증
- [IGDB API](https://api-docs.igdb.com/): 발견용 메타데이터, 인증과 이용 조건 때문에 필수 연동하지 않음

### System Atlas

공통 시스템 분류는 질문을 빠뜨리지 않기 위한 상위 지도다.

- 핵심 플레이: 조작, 전투, 탐험, 퍼즐, 스테이지, PvE·PvP
- 플레이어·캐릭터: 능력, 상태, 역할, 빌드, AI 동료
- 성장: 레벨, 장비, 스킬, 승급, 진화, 계정 성장
- 수집·제작: 캐릭터, 장비, 카드, 펫, 도감, 제작, UGC
- 경제: 통화, 자원, 획득, 변환, 소비, 교환, 인플레이션 제어
- 보상: 퀘스트, 업적, 로그인, 스테이지, 위험 대비 보상
- 콘텐츠: 메인, 던전, 레이드, PvP, 이벤트와 난이도
- 소셜: 친구, 길드, 협동, 랭킹, 신고와 운영
- BM: 구매, 상점, 패키지, 확률형 상품, 패스, 광고, 구독
- 리텐션: 일·주간 주기, 복귀, 행동력, 알림, 휴면 회복
- 메타·라이브 운영: 시즌, 이벤트, 컬렉션, 업데이트와 운영 주기
- UX·접근성: 홈, 정보 구조, 진입·이탈·복구 동선, 알림과 보조 기능
- 계정·플랫폼: 저장, 동기화, 교차 플랫폼, 권한과 지역 규칙
- 세션·네트워크: 매칭, 로비, 연결, 이탈, 재접속과 보상 정산
- 실패·회복: 재도전, 체크포인트, 손실, 보호와 악용 방지
- 운영 기반: CS, 제재, 복구, 로그, 텔레메트리와 실험

overlay는 다음 축을 조합한다.

- 장르: 액션, RPG, 전략, 시뮬레이션·경영, 퍼즐, 내러티브·어드벤처,
  생존·제작 등
- 플레이 방식: 싱글, 협동, PvP, 비동기 소셜, 지속형 월드
- 플랫폼: PC, 콘솔, 모바일, 웹과 입력·세션 제약
- 사업·운영: 패키지, F2P, 구독, 광고, 시즌형 라이브 운영, UGC

각 질문은 `required-candidate`, `conditional`, `optional`,
`not-applicable`, `unknown` 중 하나를 갖는다. `required-candidate`도 설계 의무가
아니라 분석 우선순위가 높은 후보를 뜻한다.

## 분석 흐름

### 0. 의사결정 경계 정의

“이 게임을 분석해 줘” 대신 이번 분석으로 결정할 질문을 적는다. 예를 들어
“10분 세션 안에서 전투 보상과 장기 성장의 연결 방식을 결정한다”처럼 범위를
좁힌다.

### 1. 레퍼런스 역할 선택

직접 경쟁작, 핵심 시스템 우수 사례, 운영·BM 비교작을 선정하고 선정 이유와
비교 질문을 기록한다.

### 2. 증거 계획

공식 사이트, 패치 노트, 공개 위키, 직접 플레이, 스크린샷과 영상에서 무엇을
확인할지 정한다. 플레이 자료가 없으면 해당 항목을 `not-observed`로 남긴다.

### 3. 시스템 발견

평가를 미루고 확인된 시스템을 목록화한다.

- 대분류, 시스템명, 하위 시스템
- 화면·문서 근거
- 확인된 규칙
- 추정 규칙
- 추가 확인 정보
- 확신도와 적용 overlay

### 4. 관계 모델링

각 시스템을 `input → process → output → connected systems`로 정리하고 다음
관계를 그린다.

- 플레이어 행동 루프
- 핵심, 세션, 메타 루프
- 통화와 자원의 획득, 변환, 소비
- 잠금 해제, 진입 조건과 게이트
- 시스템 의존성과 실패 전파
- 일간, 주간, 시즌 운영 주기
- UX 진입, 이탈, 오류와 복구 동선

### 5. 심층 분석 우선순위

다음 항목을 점수 또는 근거 문장으로 평가한다.

- 현재 프로젝트와의 관련성
- 플레이어 경험 영향
- 성장·경제 영향
- 차별화 가능성
- 근거 강도와 불확실성
- 추가 조사 비용

### 6. 개별 시스템 심층 분석

각 시스템은 다음 순서로 분석한다.

1. 목적 가설
2. 입력과 진입 조건
3. 상태와 규칙·예외
4. 출력, 보상과 피드백
5. 연결 시스템과 의존성
6. 경제·성장·콘텐츠·운영 영향
7. 실패, 악용, 회복과 접근성
8. 근거와 반례
9. 미확인 정보와 검증 방법

### 7. 게임 간 비교

기능 유무만 비교하지 않는다. 같은 플레이어 문제를 각 게임이 어떤 규칙,
비용, 피드백과 운영 방식으로 해결하는지 비교한다. 버전·지역·플랫폼 차이는
별도 열로 유지한다.

### 8. 기획 적용

각 통찰은 다음 구조를 갖는다.

- 레퍼런스에서 확인한 원리
- `adopt`, `adapt`, `reject`, `hold`
- 현재 프로젝트의 목표와 제약
- 그대로 복제하지 않기 위한 변형과 차별화
- 예상 효과, 위험과 부작용
- 필요한 시스템·콘텐츠·UX·운영 변경
- 검증할 프로토타입, 플레이테스트 질문과 지표
- 근거 ID와 미확인 항목

`adopt`도 자동 승인이 아니다. 모든 설계 전환은 `pending-review` 상태로 Studio의
시스템 명세 후보에 연결된다.

### 9. 용어 동기화와 사람 검토

새 개념과 표현을 용어 사전 후보로 추출하고 충돌을 검사한다. 승인된 용어
snapshot과 분석·제안 결과를 결속한 뒤 사람이 근거, 전환 결정과 용어를 함께
검토한다.

`verification-queue`는 마지막 부록이 아니라 모든 단계에서 갱신한다.

## 결과물과 파일 구조

```text
reference-intelligence/
  brief.md
  reference-set.yml
  evidence-register.yml
  system-inventory.json
  system-maps/
  analysis-priority.md
  deep-dives/
  comparison-matrix.md
  transfer-decisions.md
  verification-queue.md
  glossary/
    terms.json
    glossary.ko.md
    glossary.en.md
    terminology-findings.md
    glossary-receipt.json

```

공통 결과는 제품별로 다음과 같이 투영한다.

- Career: 기존 `reverse-design-document`, `game-analysis-report`와 포트폴리오용
  설명으로 변환한다.
- Studio: `reference-system-analysis`, `reference-comparison`,
  `design-transfer-decision`을 만들고 승인 후 `system-specification` 후보로 넘긴다.

## 프롬프트 단계

새 공통 스킬 `analyze-game-design-references`는 한 번에 모든 판단을 만들지 않고
다음 프롬프트 단계를 순서대로 실행한다.

1. 조사 질문과 결정 경계 작성
2. 레퍼런스 역할 선정과 편향 확인
3. 증거 수집 계획과 출처 등급 지정
4. 평가 없는 시스템 목록화
5. 시스템 지도와 loop 모델링
6. 심층 분석 우선순위 선정
7. 우선 시스템의 규칙·상태·경제·UX 분석
8. 게임 간 해결 원리 비교
9. `adopt/adapt/reject/hold` 설계 전환 제안
10. verification queue와 glossary 후보 갱신

각 단계는 이전 산출물의 ID를 입력으로 받고, 확인되지 않은 내용을 사실처럼
승격하지 않는다.

## 용어 사전 모델

### 구조

공통 용어 사전은 제품 전반에서 재사용하는 개념을 담고 프로젝트 overlay는 현재
프로젝트의 세계관, 시스템과 문체에 따른 표현을 추가한다. 프로젝트 overlay가
공통 정의를 바꾸려면 충돌과 변경 이유를 명시하고 사람 승인을 받아야 한다.

각 용어는 다음 필드를 가진다.

- `termId`: 언어 중립 ID, 예: `TERM-PLAYER-POWER`
- `koPreferred`, `enPreferred`
- 정의, 적용 범위와 문맥
- 약어와 허용 변형
- 금지·폐기 표현과 대체 `termId`
- 번역하지 않는 표현
- 대소문자, 띄어쓰기, 복수형과 조사 사용 지침
- 올바른 사용 예와 혼동되는 개념
- 근거·결정 ID
- `proposed`, `approved`, `deprecated` 상태
- 승인자, 버전과 변경 시점

화면 라벨, 내부 변수명, 플레이어 대상 표현처럼 문맥에 따라 다른 표현은 별도
문맥 필드로 관리하고 하나를 다른 하나의 오기로 취급하지 않는다.

### 수명주기

```text
기존 문서·분석·사용자 입력
  → 용어 후보 추출
  → proposed 등록
  → 동의어·다의어·번역·금지어 충돌 검사
  → 사람 승인
  → approved glossary snapshot + SHA-256
  → 문서 작성·검증
  → 변경 영향 목록
  → deprecated + replacement
  → 사람 승인 후 문서별 이행
```

새 공통 스킬 `maintain-game-design-glossary`가 이 수명주기를 담당한다.
`polish-game-design-writing`은 승인된 snapshot을 읽어 경고를 만들 수 있지만 의미를
판단해 자동 치환하지 않는다.

### 차단과 경고

다음은 문서 승인 또는 용어 검토 완료 선언을 차단한다.

- 하나의 개념에 같은 범위의 표준어가 둘 이상 승인됨
- 다른 개념이 같은 범위에서 구분 불가능한 표준어를 사용함
- 이중 언어 문서가 필수 한국어·영어 대응을 잃음
- 결속된 용어 사전 버전이나 해시가 사라지거나 달라짐
- 문자열 자동 치환이 의미를 바꾸려 함

다음은 경고로 보고하고 사람이 결정한다.

- 승인되지 않은 새 용어
- 금지·폐기 용어 사용
- 설명 없는 약어
- 대소문자, 띄어쓰기, 복수형 또는 표기 불일치
- 한국어 문서의 불필요한 영어 표현
- 같은 개념의 번역 불일치

한국어 자연스러움, 영어 문장 품질, 용어 일관성, 설계 타당성은 서로 다른
검사다. 하나의 검사 통과를 다른 검사 통과로 간주하지 않는다.

## 오류와 불완전 자료 처리

- 웹 자료를 열 수 없으면 `unavailable`로 기록하고 다른 근거로 진행한다.
- 직접 플레이·스크린샷이 없으면 `not-observed`로 유지한다.
- 자료가 충돌하면 버전, 플랫폼, 지역, 계정 상태별 관찰로 분리한다.
- 적합한 overlay가 없으면 공통 온톨로지로 진행하고 새 overlay를 `proposed`로 둔다.
- 비교 게임이 세 개보다 적어도 단일 분석은 허용하되 비교 결론을 확정하지 않는다.
- 유료·로그인 서비스가 없어도 분석을 막지 않는다.
- 근거가 약한 통찰은 설계 제안으로 승격하지 않고 verification queue에 남긴다.
- 용어 사전이 불완전하면 초안은 만들 수 있지만 “용어 검토 완료”로 표시하지 않는다.
- 진단에는 비공개 원문, 자격 증명, 절대 경로나 불필요한 사용자 정보를 넣지 않는다.

## 테스트와 수용 기준

### 구조와 결정성

- 같은 입력, 같은 evidence와 overlay는 같은 ID, 정렬과 결과를 만든다.
- 공통 온톨로지와 장르·플랫폼·BM overlay 병합이 중복 없이 결정적이다.
- `required-candidate`가 자동 설계 의무로 변환되지 않는다.
- 버전·플랫폼이 다른 상충 근거가 한 사실로 합쳐지지 않는다.

### 근거와 분석

- 사실, 추론, 가설, 반례와 미확인 항목이 스키마상 구분된다.
- 지원 근거가 없는 리텐션·매출·BM 인과 주장은 거부된다.
- 시스템 지도에 없는 연결 ID, 순환 오류와 고아 ID가 검출된다.
- 직접 경쟁작·우수 사례·운영 비교 역할과 질문이 결속된다.
- `adopt/adapt/reject/hold`가 근거, 프로젝트 제약과 검증 계획 없이 승인되지 않는다.

### 제품 투영

- 같은 공통 분석이 Career와 Studio에서 같은 근거 ID를 유지한다.
- Career 결과가 Studio 설계를 자동 변경하지 않는다.
- Studio 제안은 사람 승인 전 `pending-review`다.
- 웹·유료 서비스 없이 사용자 제공 자료만으로 흐름이 완료된다.

### 용어 사전

- 한국어·영어 표준어, 약어, 금지어와 문맥별 라벨 충돌을 검출한다.
- 용어 사전 hash·버전이 다른 문서를 검토 완료로 승인하지 않는다.
- 폐기 용어가 replacement 없이 삭제되지 않는다.
- 경고가 원문을 자동 수정하지 않는다.
- 한국어와 영어 문서에서 같은 `termId`가 서로 다른 의미로 사용되면 차단한다.

### 적대적·비공허성 검증

- 근거 없는 BM 결론, 사실로 위장한 추정, 다른 버전의 스크린샷을 주입하면 실패한다.
- 외부 문서의 프롬프트 지시가 실행 흐름이나 승인 상태를 바꾸지 못한다.
- overlay, transfer trace 또는 glossary hash 검사를 제거한 mutation에서 테스트가 실제로
  실패한다.
- 패키징된 Studio·Career의 공통 스키마와 원천 스키마가 byte-exact로 일치한다.

## 완료 조건

- 공통 분석 스킬과 용어 관리 스킬이 설치 가능한 공통 모듈로 제공된다.
- Studio와 Career 라우팅, 프롬프트, 템플릿과 사용자 가이드가 새 흐름을 설명한다.
- 레퍼런스 분석은 출처가 없거나 확인하지 못한 내용을 사실로 쓰지 않는다.
- 기획 적용 결과는 사람 승인 전 기존 명세를 수정하지 않는다.
- 용어 사전의 승인, snapshot, 문서 결속, 폐기와 영향 분석이 실행형 테스트로
  검증된다.
- 기존 역기획, 시스템 설계, 문장 검수와 기억 기능은 새 기능이 꺼지거나 자료가
  부족해도 계속 동작한다.
